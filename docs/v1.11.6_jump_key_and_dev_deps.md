## 2. 점프 키 명세

### 원인

v1.11.4는 이동 키를 요청에서 추출하게 만들었지만 점프는 `space`로 하드코딩된 채였다.

```python
await self._verification_call(contract, "unity_send_key", {
    "key": "space", "action": "tap", "duration": 0.08,   # 항상 space
})
```

요청이 "W키로 점프"인 게임은 `wKey`만 읽으므로 `space`에 반응하지 않는다. **게임은 요청대로
동작하는데 검증이 자기 가정 때문에 실패시키는** 구조로, v1.11.4에서 고친
`player_did_not_move_right`와 정확히 같은 실패 양상이다.

### 수정

요청에서 점프 키를 추출해 `VerificationSpec.jump_key`에 담고, 측정과 체크리스트가 이를 쓴다.

```python
_JUMP_KEY_SCHEMES = (
    (re.compile(r"\bw\s*(?:키|key)?\s*(?:로|으로)?\s*(?:점프|jump)", re.I), "w"),
    (re.compile(r"(?:위쪽\s*방향키|up\s*arrow|uparrow)\s*(?:키|key)?\s*(?:로|으로)?\s*(?:점프|jump)", re.I), "upArrow"),
)
```

| 요청 | `jump_key` |
|---|---|
| "W키로 점프하게 만들어줘" | `w` |
| "위쪽 방향키로 점프하게 만들어줘" | `upArrow` |
| "Space 점프를 고쳐줘" | `space` |
| (미지정) | `space` |

패턴은 **키 이름과 점프 단어가 인접할 때만** 매칭한다. 문장 어딘가에 `w`가 있다고
점프 키로 오인하지 않는다.

`VerificationContract.observe()`는 이미 `{"space", "spacebar", "w", "uparrow"}`를 점프
입력으로 인정하고 있어 별도 수정이 필요 없었다.

## 3. 개발 의존성

`pytest`가 의존성에 없어 테스트 실행이 매번 `uv run --with pytest --with pytest-cov ...`
형태였다. v1.11.2 보고서가 P2로 지적한 뒤에도 계속 우회해 왔다.

```toml
[dependency-groups]
dev = [
    "pytest>=8.0",
    "pytest-cov>=5.0",
]
```

이제 표준 명령이 그대로 동작한다.

```bash
uv run python -m pytest tests/
```

## 6. 남은 과제

1. **빈 씬 전체 E2E (최우선)**: 지금까지의 `verified` 두 건은 모두 `--repair-existing`,
   즉 기존 산출물 수정 결과다. **빈 씬에서 요청 하나로 제작 후 검증까지 통과한 사례는
   v1.9 독립 검증 도입 이후 한 건도 없다.** 이 프로젝트의 간판 시나리오이므로 다음
   사이클의 최우선 과제다. 실행 방법은 정해져 있다 — 새 씬 경로를 지정하고
   `--repair-existing` 없이 `--prompt-file`로 돌린다.
2. **repair 반복 효율**: v1.11.3 실행에서 3개 사이클 모두 `FIX_MAX_ITERS=20`을 소진했다.
   다만 v1.11.4에서는 한도를 다 쓰고도 버그를 고쳤으므로, "비효율이지만 작동"인지
   "한도 때문에 실패"인지 아직 구분되지 않았다. **1번 E2E가 이 답을 준다** — 빌더까지
   포함된 긴 실행에서 한도가 실제 병목인지 드러나므로, 그 전에 손대면 중요하지 않은
   것을 최적화할 위험이 있다.
3. **퇴화 요청 처리** (v1.11.2 §4.1 이월): `추가해` 같은 문맥 의존 요청은 행동 언어가
   없어 정적 검증만으로 통과한다. 대화 맥락 반영 또는 별도 코드 분리가 필요하다.
4. **외부 경계 테스트** (v1.11.2 §4.3 이월): `mcp_client.py` 19%, `main.py` 0%.
