# v1.12.1 — 계획이 중단되지 않고, 규칙이 철자 대신 동작을 본다

v1.12.0이 계획 모드를 켜자 [STATUS A7](STATUS.md)이 라이브로 재현됐다 — 마일스톤
하나가 실패하자 뒤의 둘이 통째로 날아갔다. 그것을 고치고 나니 남은 병목이 드러났고,
**같은 부류의 결함이 하루에 셋**이었다.

---

## 1. 계획이 하나의 실패로 전체를 버렸다

```text
20260809_132123   mode=plan  마일스톤 5개
  m1 Initialize Project and Scene       completed   남은예산 53
  m2 Create Player and Camera           completed   남은예산 29
  m3 Implement Player Movement Logic    failed      남은예산  5
  → 계획을 중단합니다
```

**m4(카메라 추종)와 m5(씬 설정)는 실패한 m3에 의존하지 않는데도 실행조차 못 했다.**
기록된 plan 모드 15회에서 계획된 71개 중 39개가 이렇게 사라졌고 11/15회가 중단이었다.

`_run_plan`이 실패를 기록하고 **다음 마일스톤을 계속한다.** 예산이 바닥나면 그때
멈추는 가드는 그대로다. 끝에 `plan_finished`로 완료·실패·미착수·남은예산을 남긴다.

> 옛 동작을 고정하던 테스트 하나(`..._then_aborts`)를 새 동작으로 갱신했다. 왜
> 바뀌었는지는 그 테스트의 docstring에 실측과 함께 남겼다.

## 2. 규칙이 철자를 검사하고 있었다 — 세 번째와 네 번째

v1.12.0이 `keyboard_null_check_missing`에서 찾은 것과 같은 부류가 둘 더 있었다.
영수증 145건에서 **각 규칙이 repair를 2사이클 이상 그대로 통과했는지**(모델이 못
고쳤는지) 셌다.

```text
규칙                           등장   비수렴
undefined_compare_tag          11      3
fall_respawn_check_missing      5      3   ← 60%
camera_z_accumulates_offset     5      2
keyboard_null_check_missing     3      2   (v1.12.0)
idle_velocity_not_zeroed        2      2
legacy_input_api                1      1
```

### 2.1 `idle_velocity_not_zeroed`

규칙은 `.linearVelocity = new Vector3(0, ...)` **한 형태만** 인정했다. 모델이 쓴 것은:

```csharp
// Zero out X velocity when idle to satisfy policy check
if (moveX == 0) { velocity.x = 0f; }
...
rb.linearVelocity = velocity;
```

**모델이 정책을 만족시키려고 주석까지 달아 가며 쓴 코드**를 규칙이 거부했고, repair
4사이클이 같은 위반을 반복했다(`20260809_132831`). 지역 벡터 경유·직접 생성·
`Vector3.zero`를 모두 인정하게 했다. 실제로 0으로 만들지 않는 코드는 여전히 걸린다.

### 2.2 `fall_respawn_check_missing`

```python
if "spawnPosition" not in code or ...
```

**식별자 이름을 문자 그대로 요구했다.** 모델이 `startPosition`·`initialPos`를 쓰면
아무리 옳게 구현해도 통과할 수 없다. 동작 셋으로 바꿨다 — 시작 위치를 기억하고
(`x = transform.position`), 높이를 견주고(`.y <`), 그 값으로 되돌린다
(`transform.position = x`). 이름은 무엇이든 된다.

### 2.3 손대지 않은 것

- **`undefined_compare_tag`**(11/3)는 철자 검사가 아니라 진짜 결함 탐지다 —
  프로젝트에 없는 태그는 런타임에 던진다. 비수렴의 원인은 규칙이 아니라 모델이 계속
  `CompareTag`를 쓰는 쪽이고, v1.11.26이 그 반대편(태그 설정 도구 부재)을 다뤘다
- **`camera_z_accumulates_offset`**(5/2)는 특정 결함 패턴 탐지이고 v1.11.15가 이미
  오탐을 걷어냈다. **근거 없이 건드리지 않았다**
- `keyboard_current_missing`·`linear_velocity_missing`은 API 이름 자체라 동의어가 없다

## 3. 검증

### 3.1 라이브 — 계획 모드 3회

| 실행 | 완료 | 실행된 마일스톤 | 중단 | 비고 |
|---|---|---|---|---|
| 132123 | 2 | 3 / 5 | **예** | A7 수정 전 |
| 132831 | 1 | 4 / 5 | 아니오 | 계획 지속만 |
| 133614 | **3** | **5 / 5** | 아니오 | 규칙 둘까지 |

**마지막 실행에서 마일스톤 5개가 전부 실행됐고 3개가 완료됐다.** `fall_respawn`
위반은 1회 뜬 뒤 다음 사이클에서 사라졌다 — 이전에는 그것이 끝까지 남았다.

### 3.2 단위 테스트

**321 → 328건**, subtest 52 → 59건. 전부 통과.

- 실패한 마일스톤 뒤의 것이 실행되고, 예산이 바닥나면 여전히 멈춘다
- 수평 속도를 0으로 만드는 세 형태가 통과하고, 안 만드는 것은 걸린다
- 시작 위치 식별자 이름 넷이 모두 통과하고, 기억만 하거나 아예 없으면 걸린다

### 3.3 측정하지 않은 것

- **예산 산수가 맞지 않는다.** 마일스톤마다 12 + 재시도 12를 태우면 5개 계획에
  60은 모자란다(필요 120). 세 실행 모두 남은 예산 0으로 끝났다. **아직 안 고쳤다**
- **긴 명령은 여전히 실패한다.** 마지막 실행의 판정은 `failed`이고, 막은 것은
  `player_fell_during_spawn_check` — 플레이어가 스폰에서 떨어진다. 이것은 규칙
  충돌이 아니라 **진짜 게임 결함**이고, 그것이 보이게 된 것이 이 사이클의 진전이다
- 각 조건이 1회씩이다
- `undefined_compare_tag`·`camera_z_accumulates_offset`의 비수렴은 미해결
