# v1.11.19 — 정적 검사가 빌더 산출물을 보지 못했다

`policy_lint`는 **요청이 명시한 스크립트 경로만** 검사한다. 자연스러운 요청은 스크립트
경로를 말하지 않으므로, **빌더가 스스로 만든 스크립트는 한 번도 검사되지 않았다.**

---

## 1. 배경 — v1.11.18의 잘못된 결론을 바로잡다가 나왔다

v1.11.18 §3.1은 코인 실행을 두고 "획득도 점수도 구현되지 않았다"고 적었다.
**그것은 틀렸다.** 디스크의 `PlayerMovement.cs`에 코인 로직이 없어서 그렇게 읽었는데,
그 파일은 이후 같은 Unity 프로젝트에서 돌린 순찰 실행 두 번이 덮어쓴 것이었다.
해당 문서에 정정을 넣었다.

실행 로그를 보면 코인 로직은 정상적으로 쓰였다.

```text
write #1  PlayerMovement.cs  2385자  → status: error (입력 게이트 차단)
write #2  PlayerMovement.cs  2395자  → status: ok
          메서드: Awake, Update, FixedUpdate, OnCollisionEnter,
                  OnCollisionExit, OnTriggerEnter, GetScore
unity_add_component → {"added":"PlayerMovement","path":"Player"}
```

문제는 그 코드의 내용이었다.

```csharp
void OnTriggerEnter(Collider other) {
    if (other.CompareTag("Coin")) { score++; Destroy(other.gameObject); }
}
```

```text
ProjectSettings/TagManager.asset : tags: []
```

**프로젝트에 `Coin` 태그가 없다.** 트리거가 걸리는 순간
`Tag: Coin is not defined`를 던진다.

`policy_lint.py:74-76`에는 정확히 이것을 잡는 `undefined_compare_tag`가 있다.
그런데 그 실행의 영수증은 `failures: []`였다.

## 2. 원인 — 검사 대상 목록이 요청 문장에서만 온다

```python
# VerificationContract.__post_init__ (수정 전)
self.policy_violations = lint_scripts(
    self.spec.request, self.spec.asset_paths, self.project_dir
)
```

`spec.asset_paths`는 **요청 문장에서 뽑은 경로**다. 코인 요청을 넣어 보면 이렇다.

```text
요청이 명시한 asset_paths : ['Assets/Scenes/IxCoinScore.unity']
그 목록으로 lint          : 위반 0건   ← 스크립트를 아예 안 봄
파일을 직접 지정해 lint    : ['undefined_compare_tag:...:Coin']
```

씬 하나뿐이다. `PlayerMovement.cs`는 빌더가 만든 것이라 요청 문장에 없고,
**검사 대상에 들어간 적이 없다.**

이 저장소가 `Assets/Scripts/...`를 문장에 적어 둔 대형 프롬프트로 초기 개발을 했기
때문에 지금까지 드러나지 않았다. 그 프롬프트들에서는 lint가 돌았다.

## 4. 변경 내용

### 4.1 이 세션이 쓴 스크립트를 검사 대상에 넣는다

`VerificationContract`가 이미 `session_scripts` 필드를 갖고 있었지만 아무도 채우지
않는 죽은 필드였다. `agent.py`가 `known_session_scripts`를 넘기고, lint는
`asset_paths ∪ session_scripts`를 본다.

`policy_lint` 위반은 모든 단계를 차단하므로 판정을 바꾸는 변경이다. §3의 재생이
그 대가를 정확히 말해 준다 — **7/29 이후 78개 실행 중 5개가 `verified`에서
`failed`로 바뀌고, 그 다섯은 전부 실제로 예외를 던지는 코드다.**

### 4.2 수정 안내가 기능을 지우지 않게 한다

기존 `undefined_compare_tag` 안내는 이랬다.

> 해당 CompareTag 호출이 포함된 분기 또는 OnTriggerEnter 메서드를 코드에서 완전히
> 삭제한다.

접지 판정(`CompareTag("Ground")`)에는 맞는 안내였다. 그런데 검사가 빌더 산출물까지
보게 되면 **그 분기가 사용자가 요청한 기능인 경우**가 생긴다 — 코인 획득, 골인 판정.
삭제하면 결함 대신 기능이 사라진다.

v1.11.18이 마커 컴포넌트 패턴을 열어 두었으므로 그쪽으로 안내를 바꿨다.

> 프로젝트에 `Coin` 태그가 없어 그 CompareTag는 런타임에
> `Tag: Coin is not defined`를 던진다. 태그를 만들지 말고 마커 컴포넌트로 바꾼다 —
> `public class Coin : MonoBehaviour {}`를 별도 파일로 쓰고 `unity_add_component`로
> 해당 오브젝트들에 붙인 뒤, 조건을 `other.GetComponent<Coin>() != null`로 바꾼다.
> **요청이 그 분기의 동작을 요구했다면 분기를 삭제하지 말고 조건만 바꾼다.**
> 접지 판정이라면 대신 `contact.normal`을 쓴다.

태그 이름은 실패 문자열에서 뽑아 넣는다(`policy_lint:` 접두사가 붙은 형태와 붙지 않은
형태를 모두 받는다).

## 5. 검증

### 5.1 단위 테스트

**251 → 254건**, subtest 43건. 전부 통과.

- 빌더가 쓴 스크립트가 검사된다
- `session_scripts`가 비면 같은 결함이 보이지 않는다(대비군 — 위 테스트가 무엇을
  지키는지 고정한다)
- 수정 안내가 `GetComponent<Coin>()`을 제시하고 "삭제하지 말고"를 담는다

### 5.2 실측 재생

§3의 표가 그것이다. 로그에 남은 스크립트 158개를 실제 `lint_scripts`에 통과시켜
얻은 수치이고, 가정이 아니다.

### 5.3 측정하지 않은 것

**라이브 E2E를 돌리지 않았다.** 이 변경이 실제 실행에서 코인 요청을 `failed`로
바꾸고 repair가 마커 컴포넌트로 고쳐내는지는 확인하지 않았다. §3의 재생은 "무엇이
걸리는가"를 말해 주지만 "repair가 그것을 고치는가"는 말해 주지 않는다.

`fall_respawn_check_missing` 등 나머지 규칙이 넓어진 대상에서 오탐을 내는지도
7/29 이후 표본에서는 관측되지 않았을 뿐, 새 요청 형태에서는 미지수다.

## 6. 이 사이클이 남긴 것

열린 항목은 [STATUS.md](STATUS.md)에 있다(`AGENTS.md` §3.1).

- **B** 이 변경의 라이브 확인 — 코인 요청이 실제로 `failed`가 되고 repair가 마커
  컴포넌트로 고치는지
- **E** 정적 검사 위반이 **모든 단계를 차단**하는 기존 동작을 그대로 뒀다. 코인
  태그 하나 때문에 멀쩡한 이동·점프 측정까지 blocked가 되는데, 이 판단을 바꾸는
  것은 별개의 측정이 필요한 변경이다
- **F** v1.11.18 §3.1이 열었던 "빌더 산출물이 정적 검사 밖" 항목
