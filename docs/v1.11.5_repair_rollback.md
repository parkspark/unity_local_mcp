# v1.11.5 — repair snapshot / rollback (P1)

작성일: 2026-07-29
대상 버전: **v1.11.5**
선행 문서: [v1.11.3 repair 회귀 오판 수정](v1.11.3_repair_regression_detection.md) §6

## 1. 배경 — 실측으로 확보한 근거

v1.11.3의 실측 E2E(영수증 `20260729_094913_862_fe898db6f5.json`)가 문제를 그대로 보여줬다.

```
verify 1:   2건  ─┐
reverify 3: 1건  ─┤ ← 최선 상태
reverify 4: 2건  ─┘ ← 실제로 프로젝트에 남은 상태
```

자동 수정이 사이클 2에서 점프 버그를 실제로 고쳐 실패가 1건까지 줄었다. 그런데 사이클 3에서
이동을 고치려다 통과하던 점프를 다시 깨뜨렸고, **더 나쁜 마지막 상태가 프로젝트에 남았다.**

v1.11.3은 회귀 *판정*을 정확하게 만들었지만 회귀 *복구*는 없었다. 이번 변경이 그 공백을 메운다.

## 2. 설계

### 2.1 스냅샷 범위

자동 수정이 건드릴 수 있는 것만 캡처한다. 전체 `Assets/` 스캔은 비용이 크고 불필요하다.

| 대상 | 방식 |
|---|---|
| `Assets/Scripts/**/*.cs` | 트리 재귀 스캔 |
| `Assets/StreamingAssets/Levels/**/*.json` | 트리 재귀 스캔 |
| 씬 파일, 요청에 명시된 Assets 경로 | 명시 경로로만 캡처 |

씬 오브젝트 상태는 씬 파일을 통해 디스크에 반영되고, repair 루프는 재검증 전에 이미
저장 배리어를 강제하므로 파일 스냅샷이 사실상 전체 상태를 담는다.

**삭제 안전장치**: 명시 경로(`extra_paths`)로 들어온 파일은 복원 시 **절대 삭제하지 않는다.**
삭제 대상은 스캔 트리 안에서 스냅샷 이후 새로 생긴 파일로만 한정한다. 삭제 시 Unity가
경고를 남기지 않도록 동반 `.meta`도 함께 제거한다.

### 2.2 최선 상태 추적

매 검증 직후 상태를 점수화해 더 나으면 스냅샷을 갱신한다.

```python
_ORCHESTRATION_MARKERS = frozenset({
    "no_verification_progress", "task_time_budget_exhausted",
    "verification_regressed", "verification_rolled_back",
    "verification_spec_empty", "builder_produced_no_mutation_evidence",
})

def _repair_score(failures) -> tuple[int, int]:
    state, blocked = 0, 0
    for item in failures:
        if item in _ORCHESTRATION_MARKERS:
            continue
        blocked += item.startswith("blocked:")
        state += not item.startswith("blocked:")
    return state, blocked
```

점수는 **프로젝트 상태만** 센다. 1순위는 실질 결함 수, 동점이면 차단된 측정이 적은 쪽
(더 많이 측정된 상태가 증거가 낫다)이다.

**루프 제어 마커는 반드시 제외해야 한다.** 첫 구현은 이를 접두사
`("blocked:", "verification_")`로 걸렀는데 `no_verification_progress`가 걸리지 않아
실측에서 잘못된 롤백을 일으켰다(§4.2). 마커는 프로젝트 파일의 결함이 아니라 루프의
판단이므로, 어느 사이클의 파일을 남길지 고르는 데 영향을 주면 안 된다.

이 점수는 **어느 사이클의 파일을 남길지 고르는 데만** 쓴다. 성공 판정은 여전히
`failures`가 비어 있어야 한다 — 점수가 좋다고 통과시키지 않는다.

### 2.3 되돌리는 시점

회귀에만 특수 처리하지 않고, **루프가 어떤 이유로 끝나든** 최종 상태가 최선보다 나쁘면
되돌린다. 회귀·정체(`no_verification_progress`)·시간 예산 소진을 모두 자연히 포함한다.

```python
if config.REPAIR_ROLLBACK and best_snapshot and failures \
        and self._repair_score(failures) > best_score:
    restored = snapshot.restore(best_snapshot, config.UNITY_PROJECT_DIR)
    if restored:
        await unity_refresh_assets            # 복원한 스크립트 재컴파일
        contract = await self._collect_verification(spec)   # 실제 상태 재측정
        failures = contract.failures() + ["verification_rolled_back"]
```

**복원 후 반드시 재검증한다.** 그렇지 않으면 영수증의 증거가 방금 버린 상태를 설명하게 된다.
영수증은 프로젝트가 실제로 담고 있는 상태를 기술해야 한다.

`verification_rolled_back`은 실패 항목으로 남긴다. 롤백된 실행은 검증을 통과한 것이 아니며,
재측정이 우연히 깨끗하게 나오더라도 그것을 성공으로 주장하지 않는다는 이 프로젝트의
원칙(v1.11.2)과 일치한다. 전체 이력은 영수증 `attempts`에 남는다.

## 4. 검증

### 4.1 자동 테스트

| 지표 | v1.11.4 | v1.11.5 |
|---|---:|---:|
| 테스트 수 | 116 | **131** (+7 subtests) |
| 결과 | 116 passed | **131 passed** |

`RepairRollbackTests`는 v1.11.3 실측 시나리오와 §4.2의 거짓 롤백을 함께 고정한다.

- 2건 → 1건(최선) → 2건(회귀)로 끝나면 **디스크의 파일이 "최선" 시점 내용으로 복원**되고
  영수증 `attempts`에 `phase: rollback`과 `restored_from: reverify 2`가 남는다
- 개선만 하고 끝난 실행은 롤백하지 않는다
- `UNITY_AGENT_REPAIR_ROLLBACK=0`이면 악화 상태가 그대로 남는다(옵트아웃 확인)
- **루프 마커만 다를 때는 롤백하지 않는다** — 모델의 수정이 보존된다 (§4.2 회귀)
- 점수가 4종 마커를 무시하고, `blocked:*`는 동점 시 2차 기준으로만 쓰인다

`test_snapshot.py`는 파일 수준 동작을 고정한다 — 수정 복원, 신규 파일 삭제(+`.meta`),
삭제된 파일 복구, 명시 경로 보호, 변경 없으면 무동작, 없는 프로젝트 경로 안전 처리.

### 4.2 실측 확인 — 첫 구현의 거짓 롤백과 그 수정

`groundLayer` 설정 줄을 의도적으로 제거해 점프를 깨뜨린 뒤 `--repair-existing`으로 실행했다.

**1차 실행** (영수증 `20260729_102619_321_a3e16fad58.json`) — 롤백이 발동했지만 **잘못 발동했다.**

```
verify 1:   ['player_did_not_jump']
reverify 2: ['player_did_not_jump']
reverify 3: ['player_did_not_jump', 'no_verification_progress']
rollback 4: from=verify 1, files=['Assets/Scripts/PlayerMovement.cs']
```

모델은 사이클 중에 `groundLayer = LayerMask.GetMask("Default")`를 복구하는 **올바른 수정**을
했다. 그런데 점수 함수가 `no_verification_progress`를 실질 결함으로 세는 바람에 reverify 3의
점수가 (1,1)→(2,2)로 부풀었고, verify 1보다 나쁘다고 판단해 **모델의 수정을 버리고
주입한 결함 버전을 복원**했다.

첫 구현의 접두사 필터 `("blocked:", "verification_")`에 `no_verification_progress`가 걸리지
않은 것이 원인이다. 명시적 마커 집합으로 교체하고 2차 기준도 전체 실패 수 대신 차단 수로
바꿨다(§2.2).

**2차 실행** (동일 결함 재주입, 영수증 `20260729_103022_800_977a4ba1ee.json`)

```
verify 1:   ['player_did_not_jump']
reverify 2: ['player_did_not_jump']
reverify 3: ['player_did_not_jump', 'no_verification_progress']
rollback 단계 없음
최종 파일: groundLayer = 1; // Default layer   ← 모델의 수정이 보존됨
```

실질 결함이 내내 1건으로 동일하므로 롤백이 발동하지 않았고, 모델의 수정이 디스크에
남았다. 거짓 롤백이 해소됐음을 실측으로 확인했다.

**스냅샷 범위 실측** (실제 프로젝트)

```
Assets/Scripts/PlayerInputHandler.cs   1,332 bytes
Assets/Scripts/PlayerMovement.cs       3,392 bytes
Assets/Scenes/SampleScene.unity       18,946 bytes
변경 없을 때 → modified: [], created: []
```

3개 파일 24KB. 사이클당 스냅샷을 메모리에 들고 있어도 부담이 없고, 변경이 없으면
복원도 무동작이다.

## 5. 한계

- **"정당한" 롤백은 실제 모델 실행에서 재현하지 못했다.** §4.2의 1차 실행은 롤백 경로가
  실제로 파일을 복원한다는 것을 증명했지만, 그것은 점수 버그로 인한 거짓 발동이었다.
  자동 수정이 진짜로 상태를 악화시키는 상황(v1.11.3의 2건→1건→2건)은 의도적으로 만들 수
  없어, 정당한 트리거는 단위 테스트로만 검증했다.
- **씬 오브젝트 단위 롤백은 아니다.** 저장된 씬 파일 단위로만 되돌린다. repair가 씬을
  저장하지 않고 끝내면 그 변경은 스냅샷에 잡히지 않는다(다만 루프가 저장 배리어를
  강제하므로 실제로는 드물다).
- **점수는 실패 개수 기반이다.** "실패 1건이지만 치명적"과 "실패 2건이지만 사소함"을
  구분하지 못한다. 현재 `critical_prefixes` 개념을 점수에 반영하는 것이 후속 개선이다.

## 6. 남은 과제

1. **repair 반복 효율**: v1.11.3 실행에서 3개 사이클 모두 `FIX_MAX_ITERS=20`을 소진했다.
   repair 프롬프트가 실패 항목에 더 좁게 집중하도록 개선할 여지가 있다.
2. **점프 키 명세**: 이동은 요청의 키를 따르지만 점프는 여전히 `space` 고정이라
   다른 점프 키를 요청하면 v1.11.4가 고친 것과 같은 종류의 거짓 실패가 난다.
3. **빈 씬에서의 전체 E2E**: 지금까지의 `verified`는 모두 `--repair-existing`으로 기존
   산출물을 수정한 결과다. 빈 씬에서 처음부터 만들어 한 번에 통과하는 경로는 미검증이다.
