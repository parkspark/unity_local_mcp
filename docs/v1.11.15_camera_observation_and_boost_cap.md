# v1.11.15 — 카메라가 관찰인지 시점인지 · 부스트 상한 · 카메라 스크립트 오탐

작성일: 2026-07-30
대상 버전: **v1.11.15**
선행 문서: [v1.11.14](v1.11.14_unmapped_requirements.md)

## 1. 배경

사용자가 직접 결과를 열어보고 보고했다.

> 카메라가 플레이어를 관찰하는 게 아니라 시점으로 되어 있어서 카메라 부분이 조금 이상해서.

**영수증은 이 실행을 통과로 기록하고 있었다.** 그리고 CS 파일 오염을 피하려고 사용자가
새 프로젝트(`My project (59)`)를 만들었기 때문에, 이번 측정은 스크립트가 하나도 없는
상태에서 시작한다.

측정에 쓴 문장:

```text
2.5D 플랫포머 게임을 만들어줘. A, D키로 좌, 우로 이동하고, space 키로 점프를 함.
Shift 키를 누르면 이동하던 방향으로 빠르게 X축 직선이동을 함.
카메라는 player 를 추적하며 관찰하게 해줘.
```

추출은 v1.11.14의 어휘 수정 덕분에 처음부터 완전했다 — 검사 9개, 이동키 `d/a`,
점프키 `space`, 부스트·카메라·새 씬 정책 전부 켜짐, 미매핑 0건. **이번 사이클의 결함은
전부 추출이 아니라 판정과 게이트에 있었다.**

## 2. 결함 A — 시점 카메라가 추종 검사를 완벽하게 통과한다

`camera_follow`는 플레이어가 오른쪽으로 갈 때 카메라의 X가 증가했는지만 본다.

```python
elif camera_pair[1][0] - camera_pair[0][0] <= 1e-3:
    failed.append("camera_did_not_follow")
```

**플레이어에 붙은 카메라는 변위가 정확히 같으므로 이 검사를 완벽하게 통과한다.**
1인칭 시점은 추종의 반례인데 측정값으로는 최상의 추종처럼 보인다. 게다가 영수증에는
델타만 남아 있어 **사후에 구분할 수도 없었다** — 사용자가 눈으로 보지 않았으면 드러날
경로가 없었다.

### 2.1 어제 같은 자리에서 반대 방향을 의심했다가 되돌렸다

v1.11.14 §4.3에 적었듯, 카메라가 **달아나는** 쪽을 의심해 상한을 넣었다가 근거가
오독이어서 되돌렸다. 실제 결함은 정반대 방향이었고, 그때 재생했던 "카메라 이동이
플레이어 이동과 0.04 이내로 일치" 데이터는 **정상 추종과 시점 카메라를 구분하지
못하는 데이터**였다. 둘 다 같은 변위를 낸다.

### 2.2 변경

관찰과 시점을 가르는 성질은 변위가 아니라 **거리**다.

- `camera_is_player_viewpoint` — 측정 시작 시점의 카메라·플레이어 거리가
  `_CAMERA_MIN_GAP = 1.5`유닛 미만이면 관찰로 인정하지 않는다. 기본 캡슐이 2유닛이라
  그 안쪽에서는 플레이어가 화면에 담기지 않는다.
- `camera_player_gap`을 **영수증 증거에 기록**한다. 새 측정이 필요하지 않다 — 이미
  수집하던 절대 좌표에서 계산한다. 앞으로는 영수증만으로 두 경우를 구분할 수 있다.
- `fix_prompt`에 수정 형태를 넣었다 — 카메라를 Player의 자식으로 두지 말고 별도
  오브젝트로 유지한 뒤 LateUpdate에서 `target.position + offset`으로 따라가게 하고,
  2.5D면 offset이 Z로 물러나고 Y로 올라가야 한다(`new Vector3(0, 2, -10)`).
- 같은 내용을 `agent.py` 빌더 프롬프트에도 넣어 애초에 만들지 않게 했다.

**한계: 이 검사는 라이브에서 발동한 적이 없다.** 프롬프트 안내를 함께 넣은 뒤 다섯 번
실행하는 동안 카메라 거리가 매번 `10.198`이었다(정확히 `(0, 2, -10)` 오프셋). 안내가
결함을 예방해 검사가 걸릴 일이 없었던 것이고, 따라서 **단위 테스트로만 검증됐다.**

## 3. 결함 B — 게이트가 카메라 스크립트를 입력 스크립트로 오인해 13회 차단

첫 실행의 `builder_calls`가 이랬다.

```text
{'build': 13, 'rejected': 14, 'self_check': 3}
```

**빌더 예산의 절반이 차단으로 사라졌다.** 14회 중 13회가 같은 파일이었다.

```text
Policy blocked event-only input script Assets/Scripts/CameraController.cs:
Missing: using UnityEngine.InputSystem, Keyboard.current, Rigidbody.linearVelocity,
Update read of spaceKey.isPressed, Update jumpRequested latch, ...
missing key aKey, missing key dKey, missing key spaceKey.
```

`CameraController.cs`는 **카메라 추종 스크립트**다. Keyboard.current도 점프 래치도
접지 검사도 있을 이유가 없다. 게이트가 파일명의 `controller`만 보고 플레이어 입력
스크립트로 판정해 아홉 항목을 요구했고, 모델은 13번을 다시 썼다. v1.11.10이 되돌린
오탐과 정확히 같은 계열이다.

### 3.1 변경과 효과

파일명에 `camera`나 `follow`가 있으면 입력 스크립트 정책을 적용하지 않는다. 플레이어
스크립트(`PlayerController.cs`)는 그대로 판정한다(회귀 테스트 2건).

같은 요청을 다시 돌린 결과다.

| | 수정 전 (1차) | **수정 후 (2차)** |
|---|---|---|
| `status` | verified | verified |
| `build_stage_success` | false | **true** |
| 검증 사이클 | 3 | **1** |
| 경과 | 202.1초 | **82.8초** |
| `rejected` 호출 | **14** | 2 |

**기능 넷이 얽힌 복합 요청에서 빌더가 처음으로 혼자 끝냈다.** v1.11.14 §4.2가 "복합
요청의 빌더 완결성"을 남은 과제로 적었는데, 원인은 요청의 복잡도가 아니라 게이트
오탐이었다.

## 4. 결함 C — 부스트에 상한이 없어 140유닛 대시가 통과했다

4차 실행의 측정값이다.

```text
boost_normal  = 2.49 유닛 (0.5초)
boost_shift   = 132.8 / 150.5 / 140.1 유닛 (0.5초)  → 일반 이동의 53~60배
```

부스트 판정은 하한(`boost_min_ratio = 1.4`)만 있어 **이것이 통과했다.** 플레이어가
화면 밖으로 날아가면서 뒤이은 카메라 측정까지 망가져 `camera_did_not_follow`가 났고,
repair는 멀쩡한 카메라 코드를 고치러 갔다.

이동은 v1.11.4에서, 점프는 v1.11.9에서 같은 이유로 상한을 받았다. 부스트만 남아 있었다.

### 4.1 상한 값의 근거

기록된 부스트 측정 **28건**을 전부 뽑아 분포를 봤다.

| 구간 | 건수 | 값 |
|---|---:|---|
| 정상 | 24 | 1.00 ~ 2.31배 |
| 정상(요청이 "일정 거리 대시") | 1 | 6.60배 (16.1유닛) |
| 고장 | 3 | 53.3 / 56.2 / 60.4배 (133~150유닛) |

`boost_max_ratio = 10.0`이면 6.6배는 여유 있게 통과하고 53배는 확실히 걸린다. 28건을
새 상한으로 재생해 **통과 25 / 실패 3**이고, 실패한 3건은 전부 그 고장난 실행이다.
오탐 0.

수정 안내도 함께 넣었다 — shift를 누르고 있는 동안 매 FixedUpdate가 impulse를 다시
주면 속도가 누적된다는 것, 속도 대입으로 표현하거나 점프와 같은 rising edge 래치로
한 번만 적용하라는 것.

## 5. 결함 D — 배치가 측정을 불가능하게 만드는 경우가 또 나왔다

3차 실행의 이동 측정이 `D +2.06 / A −4.96`으로 비대칭이었다. 씬을 보면 원인이 나온다.

```text
Player    (0, 1, 0)
Platform  (5, 1, 0)  scale (4, 1, 10)  → x 3~7, 플레이어와 같은 높이
```

오른쪽 3유닛 앞이 벽이다. 부스트가 동작해도 막힌 방향에서는 거리가 같으므로 비율이
1에 붙고(측정 1.1배), **코드를 고쳐서는 절대 통과할 수 없다.** v1.11.14 §4.1의
"층을 머리 위에 쌓아 점프가 불가능했던" 것과 같은 계열이다.

`fix_prompt`의 부스트 항목에 "한쪽 이동 거리가 반대쪽보다 현저히 짧으면 그 방향에
장애물이 있다"는 판단 근거와 함께 시작 지점 좌우 8유닛을 비우라는 안내를 넣고,
`agent.py` 빌더 프롬프트에도 같은 제약을 넣었다.

**효과는 부분적이다.** 4차는 장애물이 사라졌지만(D/A 4.94/−4.94) 5차에서 다시 막혔다
(D +0.47). 안내만으로는 재발을 못 막는다 — §7의 1번이 그 후속이다.

  없었다면 부스트 통과로 기록됐을 것이다.
- 카메라 거리가 매번 10 근처다. §2의 검사는 걸릴 일이 없었다.

## 7. 남은 과제

1. **막힌 방향을 측정 실패로 오인하는 것을 하네스가 판정하게 한다.** 안내만으로는
   3·5차처럼 재발한다. 한쪽 이동이 최소 거리를 넘고 반대쪽이 그 일부에 그치면
   `movement_path_blocked` 같은 별도 코드로 갈라, repair가 입력 코드가 아니라 배치를
   보게 해야 한다. 관측 표본은 2건(2.06/−4.96, 0.47/−4.69)이다.
2. `camera_is_player_viewpoint`의 라이브 확인. 지금은 예방 안내가 결함을 막아 검사가
   발동한 적이 없다.
3. 복합 요청의 빌더 완결성은 2차 1회뿐이다(1/5). 재현성을 더 봐야 한다.
4. v1.11.14 §7의 상태 변화 검사군(P1)과 오탐률 표본 확대는 그대로 남았다.
5. 브리지 도메인 리로드·held-key 재큐잉의 Unity 통합 회귀 테스트.
