# Unity Local Agent v1.11.2 진행 현황 및 개선 보고서

작성일: 2026-07-28
대상 버전: **v1.11.2**
저장소: `unity_local_mcp`
선행 보고서: [v1.11.1 진행 현황 및 개선 보고서](v1.11.1_status_and_improvement_report.md)
변경 상세: [v1.11.2 검증 명세 신뢰성](v1.11.2_verification_spec_reliability.md)

## 1. 요약

v1.11.2는 v1.11.1 보고서가 최우선(P0)으로 지목한 **검증 공집합 성공** 결함을 해소한
신뢰성 릴리스다. 새 기능은 추가하지 않았고, "측정하지 않은 것을 성공으로 판정"하던
경로를 전부 차단했다.

작업 중 영수증 전수 조사에서 예상보다 심각한 사실이 확인됐다. **이 프로젝트가 지금까지
기록한 `verified` 영수증 3건은 전부 Play Mode를 한 번도 실행하지 않은 공집합 성공이었다.**
즉 v1.11.1까지의 "검증 통과" 실적 중 실제 런타임 측정에 근거한 것은 한 건도 없었다.

수정 후 이 3건을 새 추출 로직으로 재판정하면 2건이 정상적으로 실패로 뒤집힌다.
나머지 1건은 요청 자체가 `추가해` 한 단어여서 검증할 행동 정보가 존재하지 않는
퇴화 사례다(§4.1).

릴리스 판단은 **호스트 판정 로직은 신뢰 가능해졌으나, 실제 Unity E2E 재검증은 미완**이다.

## 2. 이번 사이클에서 한 일

v1.11.1 보고서 §5의 P0 5개 항목을 모두 구현했다.

| 항목 | 내용 | 상태 |
|---|---|---|
| P0-1 | 점프·이동·착지·부스트·카메라를 `게임` 키워드와 독립 감지 | 완료 |
| P0-2 | 행동 조건이 하나라도 추출되면 `require_gameplay=true` | 완료 |
| P0-3 | 측정 조건 0개면 `verified` 금지 → `verification_spec_empty` | 완료 |
| P0-4 | 짧은 한국어 요청 포함 명세 추출 회귀 테스트 | 완료 (11개 추가) |
| P0-5 | 영수증에 `requested_checks`/`measured_checks`/`skipped_checks` 명시 | 완료 |

추가로 계획에 없었지만 같은 결함군에 속한 우회 경로 하나를 닫았다.
`고쳐줘`가 빌드 동사로 인식되지 않아 **검증 오케스트레이션 자체가 실행되지 않고**
모델이 스스로 성공을 선언할 수 있었다. 수리 동사(`고치/고쳐/해결/repair`)를 보강했다.

구현 세부와 근본 원인 분석은 [변경 상세 문서](v1.11.2_verification_spec_reliability.md)를
참고한다.

### 3.2 영수증 전수 조사 (신규)

보관된 영수증 18건을 전수 조사했다.

| 구분 | 건수 |
|---|---:|
| 전체 | 18 |
| `verified` | 3 |
| `failed` | 15 |
| **`verified` 중 `played=false`** | **3 / 3 (100%)** |

`verified` 3건 모두 `require_gameplay=false`, `require_movement=false`,
`require_jump=false` 상태였다. 2건은 `build_stage_success=false`, 즉 **빌드 단계가
실패했는데도 최종 판정은 성공**이었다.

실패 판정이 15건으로 다수인 점은 호스트 검증이 대체로 엄격하게 동작했음을 보여준다.
문제는 통과한 소수가 전부 잘못된 통과였다는 점이다.

불필요한 Play Mode 실행은 사용자 시간을 직접 소모하므로 회귀 방지가 필요하다.

| 큐브 하나 만들어줘 | false |
| Player 오브젝트 이름을 Hero로 수정해줘 | false |
| `Assets/Scripts/Foo.cs`의 오타를 수정해줘 | false |
| `remove the unused cube from the scene` | false |
| 씬에서 안 쓰는 오브젝트를 삭제해줘 | false |
| 머티리얼 색을 빨간색으로 바꿔줘 | false (검증 자체 비활성) |

### 3.5 Unity E2E

**재실행하지 않았다.** 이번 검증은 전부 호스트 단위 테스트와 과거 영수증 재판정으로
수행했다.

이 공백은 이번 변경에서 특히 중요하다. v1.11.2는 이전까지 **실행되지 않던 Play Mode
측정 경로를 실제로 켜는** 변경이기 때문이다. 즉 지금까지 한 번도 통과 실적이 없는
코드 경로(점프 궤적 측정, 착지 판정, 입력 해제, 컴포넌트 관측)가 이제부터 매 요청마다
실행된다. 해당 경로의 실측 안정성은 미검증 상태다.

## 4. 핵심 문제점

### 4.1 퇴화 요청은 여전히 정적 검증만으로 통과 — 잔여 위험

`추가해` 같은 극단적으로 짧은 문맥 의존 요청은 행동 언어를 포함하지 않으므로
`behaviour_requested=false`가 되고, 컴파일·씬 저장 등 정적 조건만으로 `verified`가 된다.

이것을 `verification_spec_empty`로 막지 않은 것은 의도적이다. 행동을 언급하지 않은
요청(이름 변경, 오타 수정, 오브젝트 삭제)까지 Play Mode를 강요하면 과잉 검증이 되고,
§3.4의 정상 사례들이 전부 실패하게 된다.

그러나 `추가해`는 "행동과 무관한 요청"이 아니라 **직전 대화에 의존하는 불완전한 요청**이다.
현재 명세 추출은 단일 요청 문자열만 보므로 이 둘을 구분하지 못한다. 대화 맥락을
반영하거나, 지나치게 짧은 요청을 별도 코드로 분리하는 처리가 필요하다.

### 4.2 repair가 새 회귀를 만들 수 있음 (v1.11.1에서 이월)

회귀 감지는 동작하지만 변경을 원자적으로 되돌리는 snapshot/rollback이 없다.
v1.11.2에서 행동 검증이 실제로 켜지면 **repair 사이클이 이전보다 훨씬 자주 발동**하므로
이 위험의 노출 빈도가 증가한다. 우선순위를 올려야 한다.

### 4.3 외부 경계 코드의 테스트 부족 (v1.11.1에서 이월)

`mcp_client.py` 19%, `local_tools.py` 18%, `main.py`·`winfocus.py`·`winmodal.py` 0%.
MCP stdio 연결, 포트 호핑, 창 포커스, 네이티브 모달은 실패 가능성이 높은데도 자동
테스트가 없다. 특히 `winfocus`는 입력 시뮬레이션의 전제 조건이라 행동 검증 신뢰성과
직결된다.

### 4.4 개발 환경에서 기본 테스트 실행이 불편함 (v1.11.1에서 이월, 미해결)

`pytest`가 의존성에 없어 `uv run --with pytest --with pytest-cov` 형태로만 실행된다.

## 5. 개선 계획

### P0 — 완료

v1.11.1의 P0 5개 항목 전부 완료. 이번 사이클에서 신규 P0는 없다.

### P1 — Unity E2E 재검증 (최우선)

격리 Unity 프로젝트에서 다음을 1회 완주한다. 검증 대상은 **이번에 새로 켜진 측정 경로**다.

1. `--project` 선택 → 브리지·패키지 자동 보완 → 컴파일·도메인 리로드 후 재연결
2. 점프 버그 요청(§3.3의 실제 요청 문자열 사용)으로 Play Mode 행동 측정이
   실제로 실행되는지 확인
3. 측정 실패 시 repair → 재검증 사이클이 종료 조건에 도달하는지 확인
4. 입력 해제, Play Mode 종료, 영수증의 `measured_checks`가 비어 있지 않은지 확인

**완료 기준**: `measured_checks`가 채워진 `verified` 영수증 1건 이상 확보.
현재 프로젝트에는 그런 영수증이 존재하지 않는다.

### P1 — 안전한 자동 repair

1. repair 전 hierarchy·transform·component·파일 fingerprint snapshot
2. 기존 통과 조건을 보호 목록으로 고정
3. 레벨 배치 repair는 새 GameObject/Collider 생성 기본 금지
4. 새 P1 회귀 발생 시 해당 cycle 자동 rollback
5. 변경 파일·오브젝트·fingerprint를 영수증에 기록

### P2 — 퇴화 요청 처리

1. 대화 맥락을 반영하거나, 임계 길이 미만·지시대명사만 있는 요청을
   `verification_request_underspecified`로 분리
2. 해당 요청은 성공 판정 대신 구체화를 유도

### P2 — 테스트·개발 경험

- `pytest`, `pytest-cov`를 개발 의존성 그룹으로 선언하고 표준 `test` 명령 추가
- `mcp_client.py`, `local_tools.py`, `winfocus.py` 경계 테스트 추가
- 실행 로그에서 재연결 성공률, repair cycle 수, **`skipped_checks` 발생률** 집계

## 6. 완료 판정 기준

v1.11.1의 기준을 유지하되 이번 사이클 결과를 반영해 갱신한다.

| 기준 | 상태 |
|---|---|
| 행동 요청이 공집합 검증으로 `verified`되지 않음 | **충족** (§3.3) |
| 검증 명세의 요청 조건과 측정 조건이 영수증에 일치 | **충족** (P0-5) |
| 과잉 검증으로 무관한 요청이 Play Mode를 요구하지 않음 | **충족** (§3.4) |
| v1.11.2 변경 이후 격리 Unity E2E 1회 이상 완주 | **미충족** (§3.5) |
| `measured_checks`가 채워진 `verified` 영수증 확보 | **미충족** (§3.2) |
| 자동 repair가 새 치명적 회귀를 만들지 않거나 즉시 rollback | **미충족** (§4.2) |
| Save Scene 모달·미해제 입력·미종료 Play Mode 0건 | 미검증 |
| 브리지 재연결과 프로젝트 identity 검증이 자동 테스트에서 통과 | 부분 충족 |

## 7. 결론

v1.11.1 보고서는 "가장 위험한 결함은 기능 실패가 아니라 검증 조건이 빠진 요청을 성공으로
판정할 수 있는 것"이라고 진단했다. v1.11.2는 그 진단이 옳았음을 데이터로 확인했고
— 과거 `verified` 3건이 **전부** 공집합 성공이었다 — 판정 로직 차원에서 이를 닫았다.

다만 이 작업의 성격은 **잘못된 성공을 실패로 되돌린 것**이지, 성공을 만들어낸 것이 아니다.
현재 이 프로젝트에는 실제 Play Mode 측정에 근거한 `verified` 영수증이 단 한 건도 없다.
다음 사이클의 목표는 새 기능이 아니라 **`measured_checks`가 채워진 첫 번째 정당한
검증 통과를 확보하는 것**이어야 한다.
