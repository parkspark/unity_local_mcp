# v1.11.9 — 점프 상한 검증 · 하네스의 스크립트 대필 제거

작성일: 2026-07-29
대상 버전: **v1.11.9**
선행 문서: [v1.11.8](v1.11.8_builder_stage_completeness.md)

> **검증 범위 고지**: 단위 테스트와 새 씬 전체 E2E를 모두 실행했다. 점프 물리는
> 고쳐졌지만 `build_stage_success`는 `true`에서 `false`로 후퇴했다. §3.2와 §4에
> 실측값과 그 대가를 적었다.

## 1. 배경

v1.11.8은 `build_stage_success=true`, `attempts=1`, `measured 5/5`, `skipped []`로
빌더 자체 완결성 목표를 달성했다. 그런데 같은 영수증
`logs/receipts/2026/07/29/20260729_144252_934_a8975f4d2e.json`의 실측값은 이랬다.

```text
player_jump_delta Y   = +19.962933      (jumpForce=10, 정상이면 약 5)
player_jump_peak_y    = 21.062933
jump_landed           = false
종료 시 linearVelocity = (0, -5.70, 0)   ← 아직 낙하 중
```

플랫포머 캐릭터가 20유닛 솟아올라 착지하지 못한 채 검증이 끝났는데 `status=verified`가
나왔다. 이동에는 `movement_max_speed=25.0` 상한이 있는데 **점프에는 하한
(`jump_min_rise=0.5`)만 있고 상한이 없었기 때문**이다. 요청에 "착지"가 없어
`require_jump_landing`도 `false`였다.

원인은 빌더가 최종 저장한 `PlayerMovement.cs`다.

```csharp
void Update() {                                   // 매 렌더 프레임
    if (Keyboard.current.spaceKey.isPressed && isGrounded) jumpRequested = true;
}
void FixedUpdate() {
    if (jumpRequested) { rb.AddForce(up * jumpForce, ForceMode.Impulse); jumpRequested = false; }
}
void OnCollisionExit(...) { isGrounded = false; }
```

`isPressed`는 레벨 트리거라 rising edge가 없다. `isGrounded`는 `OnCollisionExit`가
물리 스텝 뒤에 돌기 전까지 true로 남는다. 그래서 tap 유지 구간의 여러 Update 프레임이
래치를 다시 세우고, impulse가 중첩돼 발사 속도가 배로 커진다.

이 구현을 유도한 것은 v1.11.8이 함께 넣은 두 변경의 상호작용이다.

1. 브리지가 누른 키 상태를 매 Editor tick 재큐잉 (A/D가 한 프레임만 보이던 문제 수정)
2. 정책이 `wasPressedThisFrame`을 금지하고 `isPressed` 래치를 강제

즉 v1.11.8은 한쪽 실패 모드(엣지 유실)를 고치면서 반대쪽 실패 모드(임펄스 중첩)를
만들었고, 검증층은 상한이 없어 그것을 통과시켰다. 이 저장소가 v1.11.2부터 싸워온
"측정은 했으나 판정 기준이 없어 통과" 계열이 점프에서 재현된 것이다.

## 2. 변경 내용

### 2.1 점프 상승량 상한 (P0)

`VerificationSpec.jump_max_rise`(기본 10.0)를 추가하고 실패 항목
`player_jumped_too_high`를 도입했다. `movement_max_speed`와 같은 성격의 sanity
상한이다. 단일 impulse의 정상 상승은 약 5유닛이고, impulse가 두 번만 겹쳐도 약 20유닛이
되므로 10.0은 정상 점프를 통과시키면서 중첩을 확실히 잡는다.

`checklist()`에도 상한을 명시해 모델이 검증 기준을 미리 본다. `_FAILURE_CHECK_PREFIXES`에
등록했으므로 repair 회귀 판정에서 `jump` 검사로 정상 분류된다.

### 2.2 rising edge 래치 표준화

`wasPressedThisFrame`(엣지 유실)과 `isPressed` 단독 래치(임펄스 중첩) 둘 다 이 하네스에서는
틀린다. 직전 프레임 상태를 직접 비교하는 형태만 브리지와 물리 스텝 양쪽에서 성립한다.

```csharp
bool pressed = Keyboard.current.spaceKey.isPressed;
if (pressed && !jumpHeld && isGrounded) jumpRequested = true;
jumpHeld = pressed;
// FixedUpdate: impulse 한 번 적용 후 jumpRequested = false
```

이 형태를 시스템 프롬프트, `fix_prompt`의 실패 안내, `task_contract`의 정책 게이트
세 곳에서 동일하게 요구한다. 게이트는 Update 본문에 **자기가 다시 쓰는 부정 플래그**가
있는지로 rising edge를 판정한다. 이 조건이 `!jumpHeld`와, 충돌 콜백에서만 대입되는
`!isGrounded`를 구분한다.

### 2.3 정책 게이트의 스크립트 대필 제거 (P1)

v1.11.8의 게이트는 `unity_write_script`의 `content`를 정규식으로 직접 치환했다.

| 치환 | 문제 |
|---|---|
| `spaceKey.wasPressedThisFrame` → `.isPressed` | §1의 임펄스 중첩을 직접 유발 |
| `CompareTag("Ground")` → `(collision.gameObject != gameObject)` | 벽·천장 충돌도 접지로 판정 |

두 치환을 모두 제거했다. 게이트는 무엇이 빠졌는지 **보고**하고 모델이 다시 쓰게 한다.
하네스가 대신 고친 만큼 `build_stage_success=true`는 로컬 모델의 실력이 아니라 하네스의
실력이 되고, 영수증이 "로컬 모델이 동작하는 스크립트를 만들었는가"를 더 이상 말할 수
없게 된다. 이는 AGENTS.md §1이 E2E 대리 실행을 금지하는 것과 같은 이유다.

정의되지 않은 `"Ground"` 태그는 치환 대신 **차단**한다. 이번 세션에서 만든 새 씬에는 그
태그가 없어 `CompareTag`가 런타임 예외를 내므로, 그 경우에만 막고 `contact.normal`
기반 접지로 안내한다. 사용자 프로젝트에 태그가 이미 있는 기존 씬 작업은 영향을 받지 않는다.

`_method_body()`는 줄바꿈이 아니라 중괄호 깊이로 메서드 본문을 자른다. 이전 구현은 모델이
스크립트를 한 줄로 쓰면 FixedUpdate 문장이 Update 본문에 섞여 들어갔다.

### 2.4 `require_input_sim` 과잉 트리거 축소

v1.11.8은 `(이동|점프|move|movement|jump)` AND `(검증|확인|실제로|verify|test)`로
Play Mode + 입력 시뮬을 요구했다. "확인"과 "test"는 읽기 전용 요청에도 흔해서
"PlayerMovement 스크립트 확인해줘" 같은 요청까지 Play Mode 측정을 강제했다.

단독 단어는 `검증`/`verify`만 남기고, 나머지는 런타임 증명을 실제로 요구하는 어구
(`실제로 ~되는지`, `동작 확인`, `되는지 확인`, `actually works`)로 좁혔다. 기존 E2E
프롬프트의 "이동과 점프가 실제로 되는지 검증까지 끝내줘"는 그대로 트리거된다.

### 2.5 A/D 표기 불일치 수정

`_direct_keyboard_keys`는 `A/D`, `A·D`만 받았고 `verification.py`의 `_AD_SCHEME`은
`,`·`+`·`wasd`도 받았다. "A, D로 이동"은 검증 키는 A/D로 잡히면서 직접 키보드 정책은
적용되지 않았다. 두 정규식을 같은 형태로 맞췄다.

### 3.3 대가 — 빌더 자체 완결성 후퇴

`build_stage_success`가 `true`에서 `false`로 돌아갔다. 첫 호스트 검증에서 모든 행동
검사가 0으로 측정됐고, 그 시점의 Player 컴포넌트에 `PlayerMovement`가 아예 없었다.

```text
attempt 1 (verify)   failures = [player_did_not_move_right, d_did_not_move_right,
                                 a_did_not_move_left, player_did_not_jump, player_did_not_land]
          components = [Transform, MeshFilter, CapsuleCollider, MeshRenderer, Rigidbody]
attempt 2 (reverify) failures = []
```

원인은 게이트가 엄격해진 대가다. 빌더는 `unity_write_script`를 **15회 시도해 1회만
통과**했고(v1.11.8은 5회 중 2회), 남은 iteration이 없어 통과한 스크립트를 Player에
붙이지 못한 채 한도에 닿았다(`model_loop_completed=false`). repair 한 사이클이 부착과
재검증을 마쳤다.

차단 사유는 대부분 `Collider.bounds or Ground collision check`와 rising edge였다.
정책이 요구하는 형태를 모델이 한 번에 맞히지 못하고 반복 탐색한 것이며, 이는 검증
실패가 아니라 **예산 문제**다.

## 6. 남은 과제

1. **빌더 자체 완결성 회복 (최우선)**: `build_stage_success=true`와 점프 상한 통과를
   동시에 만족해야 한다. 지금은 정책이 요구하는 형태를 모델이 15회 탐색하느라 예산을
   소진한다. 게이트를 느슨하게 하는 것은 v1.11.8의 대필로 되돌아가는 길이므로,
   차단 메시지를 한 번에 고칠 수 있는 형태로 다듬거나 요구 형태를 시스템 프롬프트의
   예제 코드로 먼저 제시하는 쪽을 검토한다.
2. 반복 차단을 모델 호출 예산 관점에서 계측한다. 같은 사유로 N회 이상 차단되면
   해당 사유의 정확한 최소 예제를 프롬프트에 주입하는 것을 고려한다.
3. 점프 상한 10.0은 표준 중력·질량 기준의 경험값이다. 저중력 씬에서 오탐이 나면
   `jumpForce`와 `Physics.gravity`로 기대 상승량을 유도하는 방식을 검토한다.
4. 브리지 Play/Edit 도메인 리로드 재바인딩과 held-key 재큐잉의 Unity 통합 회귀 테스트.
5. 정의되지 않은 tag 설정을 성공으로 보고하는 브리지 응답을 명시적 오류로 바꾸기.
