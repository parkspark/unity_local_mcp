# v1.12.6 — 요청을 완벽히 지킨 구현이 통과할 수 없었다

v1.12.5가 벽을 치우고 나니 남은 실패가 한 곳에 몰렸다 — 부스트 비율 1.39·1.40·1.39가
문턱 1.4에 걸렸다. 계산해 보니 **요청대로 정확히 구현했을 때의 상한이 1.36**이었다.
문턱을 내리는 대신 **요청이 말한 숫자로 문턱을 세우게** 했고, 같은 조건 5회에서
`verified` **2/5**가 됐다.

---

## 1. 문턱이 요청과 다른 것을 재고 있었다

요청은 이렇게 쓴다.

```text
부스트 지속시간 0.18초
부스트 속도는 일반 이동 속도의 2배
```

호스트는 **0.5초 구간**의 이동 거리를 일반 이동과 비교해 1.4배 이상을 요구했다.
요청대로 구현하면 0.18초만 2배이고 나머지 0.32초는 일반 속도다.

```text
(0.18 × 2 + 0.32) / 0.5 = 1.36
```

**1.4를 넘을 수 없다.** 통과한 회차들은 지속시간이나 배수를 요청보다 크게 잡은
쪽이었다 — 판정이 구현 품질이 아니라 **요청 위반 정도**로 갈리고 있었다.

뿌리는 이름 하나였다. `boost_duration`이 **측정 창**과 **요청의 지속시간** 둘 다로
쓰였다. 그래서 문턱을 정할 때 둘이 같은 것처럼 보였다.

## 2. 기록된 55건이 두 형태를 보여준다

영수증 전체에서 `boost_shift / boost_normal`을 뽑았다.

```text
지속시간을 명시한 요청     실패 ≤ 1.24    성공 ≥ 1.38     기대 1.36
명시하지 않은 요청         실패 ≤ 1.22    성공 ≥ 1.96     기대 2.00
```

두 형태 모두 **성공과 실패 사이가 비어 있다.** 기존 문턱 1.4는 아래 형태에서
교정된 값인데 위 형태에 그대로 적용되고 있었고, 위 형태에서는 성공 구간
(1.38~1.46) 한가운데를 지나고 있었다.

## 3. 변경 — 요청에서 읽고, 기대치의 일부를 요구한다

```python
boost_measure_window   = 0.5     # 거리를 재는 구간. 이름을 갈랐다
boost_request_duration = 0.18    # 요청에서 읽는다
boost_speed_multiplier = 2.0     # 요청에서 읽는다

expected  = (0.18 × 2 + 0.32) / 0.5 = 1.36
threshold = 1 + (expected − 1) × 0.85 = 1.306
```

계수 0.85는 위 두 빈 구간에 **동시에** 들어간다 — 명시 요청은 1.306(빈 구간
1.24~1.38), 미명시 요청은 1.85(빈 구간 1.22~1.96). 키 입력 지연·물리 스텝
(0.02초)·가속 구간 때문에 실측이 기대치에 못 미치는 몫이다.

미명시 요청의 문턱은 **1.4에서 1.85로 올라간다.** 그쪽이 느슨했다.

같은 요청에 적힌 합격 조건("부스트 이동 거리가 일반 이동의 1.4배 이상")을 배수로
읽으면 **문턱이 자기 자신을 재게 된다.** 그래서 속도 문맥(`부스트 속도`,
`이동 속도의`)만 읽는다.

## 4. 검증

### 4.1 기록된 표본 재판정 — 역전 0건

각 영수증을 **자기 요청으로** 다시 판정했다.

```text
새로 통과   4건    1.393 · 1.393 · 1.393 · 1.378
새로 실패   0건
```

새로 통과한 넷은 전부 "요청대로 구현했는데 문턱에 걸린" 값이다. 미명시 요청의
문턱이 1.85로 올라갔지만 그 구간(1.4~1.85)에 있는 표본은 없었다.

### 4.2 라이브 — 같은 조건 5회

```text
회차      판정     측정/미측정  사이클  비율     비고
repro11  verified   17 / 0      4     1.394   벽 이름 → 다음 사이클 통과
repro12  failed     17 / 0      4     1.082   부스트가 실제로 지워진 형태 — 옳게 실패
repro13  failed     17 / 0      4     1.394   점프가 안 됨 (player_did_not_jump)
repro14  failed      9 / 8      4     —       policy_lint 루프로 측정 붕괴
repro15  verified   17 / 0      2     1.394   낙하 → 한 사이클 만에 통과
```

**`verified` 2/5.** 통과한 두 회차의 비율이 **둘 다 1.394**다 — v1.12.5까지라면
둘 다 실패했을 값이고, 이 버전이 무엇을 바꿨는지 그대로 보여준다. 부스트가 실제로
망가진 repro12(1.082)는 여전히 실패한다.

repro15는 **사이클 2회**로 끝났다 — 이 프롬프트에서 가장 짧다.

### 4.3 v1.12 계열 재현성

```text
                  verified   측정 17/0

v1.12.5 (5회)       1 / 5       5 / 5

```

원본 1회를 합쳐 **16회 중 `verified` 4회**다.

### 4.4 단위 테스트

**348 → 355건**, subtest 68건. 전부 통과. 요청 숫자 읽기, 합격 조건을 배수로
오독하지 않는 것, 두 형태의 문턱이 각각의 빈 구간에 들어가는 것, 실측 5개 값의
통과/실패를 고정한다.

### 4.5 측정하지 않은 것

- **16회 중 4회다.** 재현성은 여전히 낮다
- `build_stage_success`는 **16회 전부 `False`**
- 계수 0.85는 **두 빈 구간에 들어간다는 것 말고 다른 근거가 없다.** 표본이
  늘면 다시 봐야 한다
- 요청이 지속시간만 말하고 배수를 말하지 않으면 배수 2.0을 가정한다 — 그 형태의
  실측은 없다
- 남은 실패는 흩어져 있다 — 점프, policy_lint 루프, 부스트 구현 자체
