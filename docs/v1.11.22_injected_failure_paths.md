# v1.11.22 — 결함을 주입해 실패 경로를 실측했다

코드 변경이 없는 사이클이다. `docs/STATUS.md`의 B 항목 세 개가 "탐지는 재생으로
확인했지만 **실제 실행에서 발동하고 repair가 고치는지는 보지 않았다**"로 남아
있었다. 결함을 의도적으로 주입해 그 절반을 채웠다.

`AGENTS.md` §1.2가 허용하는 "테스트로 주입한 결함" 경로이고, 판정은 전부 호스트
검증 계층이 했다.

---

## 1. `movement_path_blocked` (B0.2) — v1.11.21

통과한 씬의 Player 오른쪽 2.5유닛에 벽을 세웠다.

```text
unity_create_gameobject TestWall  Cube  position [2.5, 1, 0]  scale [1, 3, 6]
```

| 단계 | 결과 |
|---|---|
| 1차 검증 | `movement_path_blocked:d` — **D +1.24 / A −4.96** (비율 0.25) |
| repair | `unity_modify_gameobject TestWall position [2.5, 5, 0]` → `[2.5, 10, 0]` |
| 2차 검증 | 실패 0건 — **D +4.95 / A −4.86** |
| 결과 | `verified` 57.9초, 검사 7/7 |

**repair가 스크립트를 한 줄도 건드리지 않고 벽을 위로 옮겼다.** v1.11.21이
겨냥한 것이 정확히 이 행동이다 — 기존 코드였다면 `d_did_not_move_right`가 나가고
repair는 멀쩡한 `PlayerMovement.cs`를 다시 썼을 것이다.

영수증 `logs/receipts/2026/08/05/20260805_105848_*`.

## 2. `player_has_no_renderer` (B2) — v1.11.16

같은 씬에서 Player의 `MeshRenderer`를 뗐다.

| 단계 | 결과 |
|---|---|
| 1차 검증 | `player_has_no_renderer` **한 건만** |
| repair | `unity_add_component Player MeshRenderer` |
| 2차 검증 | 실패 0건 |
| 결과 | `verified` 63.8초, 검사 7/7 |

물리는 멀쩡하므로 이동·점프 측정이 차단되지 않고 렌더링 결함 하나만 보고됐다.
v1.11.16이 이 검사를 `required_components`에 넣지 않고 별도로 판정한 이유가 그것이고,
설계대로 동작했다.

영수증 `20260805_110035_*`.

## 3. `no_object_moved_on_its_own` (B1) — v1.11.18

순찰 씬을 새로 만들고(그 자체가 재현성 표본이다) `Enemy`에서 `EnemyPatrol`을 뗐다.

| 단계 | 결과 |
|---|---|
| 빌드 | `verified` 60.9초 — `autonomous_motion {'object': 'Enemy', 'distance': 1.7016}` |
| 1차 검증(주입 후) | `no_object_moved_on_its_own` — 최대 이동 **0.0** (`Ground`) |
| repair | `unity_write_script EnemyPatrol.cs` → **`unity_add_component Enemy EnemyPatrol`** |
| 2차 검증 | 실패 0건 — `{'object': 'Enemy', 'distance': 1.7001}` |
| 결과 | `verified` 70.2초, 검사 8/8 |

수정 안내가 "스크립트만 쓰고 `add_component`를 빠뜨리는 경우가 많다"를 짚어 두었고,
repair가 실제로 부착까지 했다.

영수증 `20260805_110201_*`(빌드), `20260805_110352_*`(주입).

### 3.1 재현성

`autonomous_motion`의 실측 표본이 셋이 됐고 값이 안정적이다.

```text
20260803_225114   Enemy  1.6458
20260805_110201   Enemy  1.7016
20260805_110352   Enemy  1.7001   (repair가 다시 붙인 뒤)
```

`EnemyPatrol`의 `moveSpeed`에 측정 구간 0.8초를 곱한 값과 맞는다.

## 4. 요약

| 검사 | 주입한 결함 | 탐지 | repair가 고친 방법 | 결과 |
|---|---|---|---|---|
| `movement_path_blocked` | 벽 배치 | ✅ | 오브젝트 이동 | verified 57.9초 |
| `player_has_no_renderer` | MeshRenderer 제거 | ✅ | 컴포넌트 부착 | verified 63.8초 |
| `no_object_moved_on_its_own` | EnemyPatrol 제거 | ✅ | 스크립트 + 부착 | verified 70.2초 |

**셋 다 1사이클 repair로 복구했다.** 세 검사 모두 "탐지만 되고 고치지는 못하는"
상태가 아님이 확인됐다.

## 5. 측정하지 않은 것

- **`repair_aborted`(B0)는 여전히 미확인.** 네 번의 실행 모두 Ollama가 끊기지 않아
  그 경로를 타지 않았다. 인위적으로 재현하려면 실행 중에 Ollama를 내려야 하는데,
  그것은 결함 주입이 아니라 인프라 조작이라 하지 않았다
- **바뀐 롤백 선택(B0)도 미확인.** 이번 네 실행은 전부 롤백 없이 끝났다
- **주입한 결함은 하나씩이다.** 실제 실패는 여러 개가 얽혀 나오고, 그때도 repair가
  같은 정확도를 낼지는 이 표본이 말해 주지 않는다
- 임계값 0.5의 빈 구간(0.43~0.95)은 여전히 미관측이다. 이번 주입은 0.25로 그
  구간을 지나가지 않았다
