# v1.11.13 — Grid 검사 개선

작성일: 2026-07-30
대상 버전: **v1.11.13**
선행 문서: [v1.11.12](v1.11.12_request_shape_generalization.md)

## 1. 배경

v1.11.12가 남긴 1번 과제는 "아직 측정된 적 없는 요청 형태"였다. 세 형태를 골랐다.

- 레벨 데이터 (LevelLoader, level JSON)
- 다수 오브젝트 절차 생성 (10x20 격자 보드)
- 부스트/대시 (`require_boost`, 비율 검증)

결과: 레벨과 부스트는 통과했고, **격자는 검증 자체가 존재하지 않았다.** 그리고 측정
과정에서 무관한 결함이 하나 더 드러났다.

## 2. 결함 A — 격자 요청은 검사가 0개였다 (P0)

프롬프트는 이랬다.

```text
Assets/Scenes/GridProceduralRepro1.unity 경로에 새 빈 씬을 생성하고, 10x20 격자 보드를
Awake에서 코드로 생성하는 MonoBehaviour를 만들어줘. 카메라가 보드 전체를 담도록 배치하고,
보드가 실제로 생성되는지 검증까지 끝내줘.
```

**실행 전 정적 추출에서 이미 검사 항목이 0개였다.**

```text
requested_checks = []
behaviour_checks = []
```

`require_gameplay = game or level or behaviour`이고 `behaviour = movement or jump or
camera or boost`인데, 이 요청은 어느 키워드에도 걸리지 않는다. "생성"과 "검증"은
행동 힌트 목록에 없다.

실제 실행 영수증(`20260730_112907_394_7f86c5abea.json`):

```text
version             = 1.11.12
status              = verified          ← 통과로 판정
build_stage_success = true
requested_checks    = []
measured_checks     = []
runtime.played      = false             ← Play Mode에 들어가지도 않음
경과 시간           = 40.8초
```

**AGENTS.md §6이 무효로 규정한 그 상태다.**

> `measured_checks`가 비어 있는 `verified`는 무효다.

사용자가 "실제로 생성되는지 검증까지 끝내줘"라고 명시했는데 호스트는 아무것도 보지
않고 40초 만에 통과를 선언했다. v1.11.2가 잡은 공집합 성공이, **그때의 가드가 다루지
않는 요청 형태로 되돌아온 것이다.**

### 2.1 기존 가드가 걸리지 않은 이유

`verification_spec_empty` 가드는 이미 있었지만 조건이 `behaviour_requested`였다.

```python
if self.spec.enabled and self.spec.behaviour_requested and not self.spec.behaviour_checks():
```

`behaviour_requested`는 `_BEHAVIOUR_HINT_WORDS`(점프·이동·추종·충돌 …)로 판정한다.
격자 요청에는 그런 단어가 하나도 없다. **가드가 "행동을 말한 요청"만 지키고 있었고,
"증명을 요구한 요청"은 지키지 않았다.**

### 2.2 변경

`verification_requested`를 새로 뽑는다 — `검증`/`verify`/`검사`, 그리고
`실제로 …되는지/동작/작동/생성` 같은 구문. 여기에 `build_requested`(만들라고 한
요청인지)를 함께 걸어, **만들라고 했고 + 증명을 요구했는데 + 뽑아낼 검사가 하나도
없으면** 성공으로 끝내지 않는다.

`build_requested` 조건이 필요한 이유는 반대 방향 오류 때문이다. `현재 씬 기본 검증`
같은 순수 호스트 검증 명령도 "검증"을 포함하고 검사 목록이 비어 있는데, 그것까지 막으면
검증 명령 자체가 못 돌게 된다(회귀 테스트 2건이 실제로 이걸 잡았다).

재실행 영수증(`20260730_113236_364_a4b01c0b4d.json`):

```text
version  = 1.11.13
status   = failed
failures = ['verification_spec_empty']
```

**거짓 통과가 정직한 실패로 바뀌었다.** 이 형태를 지원하게 만든 것이 아니라, 지원하지
못한다는 사실을 숨기지 않게 만든 것이다. 구분해서 읽어야 한다.

## 3. 결함 B — 호스트 파일 도구가 프로젝트 가드를 우회했다

측정 도중 Unity Editor가 **다른 프로젝트**(`My project (58)`)에 열려 있는데 실행은
`--project "...My project (55)"`를 가리키는 상황이 생겼다. 브리지 호출은 전부 정확히
거부됐다.

```text
unity_create_scene    → Unity bridge project mismatch: expected ...(55), got ...(58)
unity_refresh_assets  → 〃
unity_create_gameobject → 〃
```

그런데 **`unity_write_script`는 성공했다.** 프로젝트 (55)에 `GridBoard.cs`,
`GridBoardGenerator.cs`, `GridBoardProcedural.cs` 세 파일이 실제로 쓰였다 — 아무도
작업하고 있지 않은 프로젝트에.

원인은 가드의 위치다. `_ensure_project_identity()`는 `mcp_client._call_impl`의
`_MUTATIONS` 분기에서만 돌고, 호스트 파일 도구(`local_tools.NAMES`)는 그 위에서
먼저 return한다. 호스트 도구는 브리지를 거치지 않으므로 브리지의 정체성을 물어본 적이
없었다.

### 3.1 변경

`local_tools` 분기에서도 같은 검사를 먼저 돌리고, 실패하면 파일을 쓰지 않는다.

```text
Unity bridge project mismatch: expected ..., got .... Host file tools write to the
--project path, so writing now would put files in a project the Editor is not
showing. Open the expected project in Unity, or restart with --project pointing at
the open one.
```

## 4. 측정 결과

전부 열려 있는 프로젝트(`My project (58)`)에서, 새 씬 경로 · `--repair-existing` 없이
실행했다.

| 형태 | 실행 | `status` | `build_stage_success` | 사이클 | 실측/요청 | 경과 |
|---|---|---|---|---:|---|---:|
| 레벨 데이터 | Level1 | verified | **true** | 1 | 5/5 | 58.6초 |
| 레벨 데이터 | Level2 | verified | false | 3 | 5/5 | 129.3초 |
| 부스트 | Boost1 | verified | **true** | 1 | 5/5 | 70.2초 |
| 부스트 | Boost2 | verified | **true** | 1 | 5/5 | 66.0초 |
| 격자 | Grid1 (v1.11.12) | ~~verified~~ | ~~true~~ | 1 | **0/0** | 40.8초 |
| 격자 | Grid2 (v1.11.13) | **failed** | false | 1 | 0/0 | 34.0초 |
| 점프(회귀) | Jump12 | verified | **true** | 1 | 6/6 | 63.8초 |

- **레벨 데이터**: `level_loaded_marker=true`를 두 실행 모두 실측했다. Level2의 첫 검증
  실패는 `a_moved_too_far` — 속도 상한을 넘은 **실제 게임플레이 결함**이고 하네스는
  정확히 잡았다. repair 2회로 통과.
- **부스트**: 부스트 비율이 `5.08/2.59`(1.96배), `5.29/2.49`(2.12배)로 하한 1.4를 넘었다.
  두 실행 모두 빌더가 혼자 끝냈다.
- **격자**: 지원되지 않는 형태임이 확인됐다(§2).
- **점프 회귀**: 이번 변경(`failures()` 조건, 호스트 도구 가드) 뒤에도 무회귀.
  사용자가 직접 돌린 1회를 포함해 점프 형태는 통산 **13/13**이다.

## 7. 남은 과제

1. **격자 형태를 실제로 지원하기.** 지금은 정직하게 실패할 뿐이다. "코드로 N개를
   생성한다"를 측정하려면 Play 중 계층의 오브젝트 수를 세는 검사(`require_object_count`
   같은)가 필요하다. 이건 새 검사 종류를 추가하는 설계 작업이므로 이번 사이클에서
   임의로 넣지 않았다. **약한 검사를 급조해 통과시키는 것이 지금 상태보다 나쁘다.**
2. 같은 종류의 공백이 더 있는지 — 요청 형태별로 어떤 검사가 뽑히는지 표로 만들어
   빈칸을 먼저 찾는 편이 실행마다 하나씩 발견하는 것보다 빠르다.
3. AGENTS.md §4의 프로젝트 경로는 고정값으로 적혀 있었다. 실행 전 `unity_ping`으로
   실제 열린 프로젝트를 확인하라는 지침으로 바꿨다(결함 B가 그 때문에 났다).
4. Rigidbody 회전 고정, 점프 상한 10.0의 저중력 씬 오탐은 v1.11.11부터 그대로 남았다.
5. 브리지 도메인 리로드·held-key 재큐잉의 Unity 통합 회귀 테스트.
