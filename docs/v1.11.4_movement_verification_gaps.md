# v1.11.4 — 이동 검증 공백 수정 (속도 상한 · 입력 키 일치)

작성일: 2026-07-29
대상 버전: **v1.11.4**
선행 문서: [v1.11.3 repair 회귀 오판 수정](v1.11.3_repair_regression_detection.md) §8

## 1. 배경

v1.11.3의 실측 E2E에서 **검증 로직 자체의 공백 2건**이 드러났다. repair 회귀 판정과는
별개로, 이동 검증이 잘못된 통과·잘못된 실패를 동시에 내고 있었다.

영수증 `20260729_100359_216_4bf6dfd4a8.json`:

```
motion_deltas = {'rightArrow': [0.0, 0.0, 0.0],
                 'd': [126.78, -3.81, 0.0],
                 'a': [-131.87, -3.98, 0.0]}
failures = ['player_did_not_move_right', ...]
```

한 실행 안에 두 결함이 동시에 있다.

- **거짓 통과**: D/A 이동이 1초에 126~131유닛인데 `d_did_not_move_right`가 뜨지 않았다.
- **거짓 실패**: 요청은 A/D였는데 `rightArrow`로 테스트해 `player_did_not_move_right`.

## 2. 공백 1 — 이동 거리 상한 없음

### 원인

`require_bidirectional` 검사가 **하한만** 봤다.

```python
elif d[1][0] - d[0][0] < self.spec.movement_min_distance:   # 2.0 이상이면 통과
    failed.append("d_did_not_move_right")
```

모델이 만든 `PlayerMovement.cs`는 매 `FixedUpdate`(초당 50회)마다
`rb.AddForce(..., ForceMode.Impulse)`를 호출한다. Impulse는 순간 속도 변화라
프레임마다 누적되어 속도가 폭주한다. 1초에 131유닛은 물리적으로 명백히 고장인데,
"2.0 이상 움직였다"는 조건은 만족하므로 통과했다.

### 수정

속도 기반 상한을 도입했다. 고정 거리가 아니라 `movement_max_speed × duration`으로
계산해 측정 시간이 달라져도 일관되게 동작한다.

```python
movement_max_speed: float = 25.0

def movement_max_distance(self, duration=None) -> float:
    return self.movement_max_speed * (self.movement_duration if duration is None else duration)
```

신규 실패 코드: `player_moved_too_far`, `d_moved_too_far`, `a_moved_too_far`.
세 코드 모두 `critical_prefixes`에 등록해 회귀 감지 대상이 되고,
`failure_check_name()`에 매핑해 최초 측정/회귀 구분도 정상 동작한다.

`fix_prompt()`에 결정적 수정 지침을 추가했다 — 지속 입력은 `linearVelocity`를 직접
설정하거나 `ForceMode.Force`로 바꾸고 최대 속도를 제한하라는 내용이다.

상한 25 u/s는 넉넉하게 잡았다. 정상적인 플랫포머(5~10 u/s)는 여유롭게 통과하고,
Impulse 폭주(130 u/s)만 걸린다.

## 3. 공백 2 — 요청한 입력 키를 무시

### 원인

요청은 "**A/D** 좌우 이동"이었는데 검증은 `rightArrow`를 하드코딩했다.

```python
if spec.require_movement:
    await measure_motion("rightArrow", "rightArrow", 0.5)   # 항상 방향키
```

모델이 만든 스크립트는 `keyboard.aKey`/`dKey`만 읽으므로 `rightArrow`에는 반응하지
않는다. **게임은 요청대로 동작하는데 검증이 자기 가정 때문에 실패시킨** 것이다.

### 수정

**(a) 요청에서 제어 방식을 추출한다.**

```python
_AD_SCHEME    = re.compile(r"\ba\s*[/,·+]\s*d\b|\bd\s*[/,·+]\s*a\b|\bwasd\b", re.I)
_ARROW_SCHEME = re.compile(r"방향키|화살표|arrow\s*keys?", re.I)
```

| 요청 | `move_right_key` | `movement_keys_explicit` |
|---|---|---|
| "A/D 좌우 이동" | `d` | True |
| "방향키로 이동" | `rightArrow` | True |
| (미지정) | `rightArrow` | False |

**(b) 표본을 서로 인정한다.** `require_movement`는 `rightArrow` 표본이 없으면
`bidirectional`의 `d` 표본을 사용한다. 같은 능력("오른쪽으로 이동")을 증명하므로
중복 측정이 필요 없다. A/D 요청에서는 별도 `rightArrow` 측정을 아예 건너뛴다
(Play Mode 재시작 1회 절약).

**(c) 미지정일 때만 대체 키를 시도한다.** 요청이 제어 방식을 명시하지 않았고 기본
키로 움직이지 않았다면, 게임이 다른 관례를 쓸 수 있으므로 대체 키로 한 번 더 측정한다.
비용은 실패 경로에서만 발생한다.

```python
if not spec.movement_keys_explicit and moved <= 1e-3:
    alternate = "d" if spec.move_right_key != "d" else "rightArrow"
    await measure_motion("rightArrow", alternate, 0.5)
```

## 5. 검증

### 5.1 자동 테스트

| 지표 | v1.11.3 | v1.11.4 |
|---|---:|---:|
| 테스트 수 | 108 | **116** (+3 subtests) |
| 결과 | 108 passed | **116 passed** |

신규 테스트는 실측 수치를 그대로 고정한다.

- A/D · 방향키 · 미지정 요청의 제어 방식 추출

- 1초 5유닛 이동 → 통과
- A/D 요청에서 `d` 표본만으로 `require_movement` 충족
- 양방향 126/131유닛 → `d_moved_too_far`, `a_moved_too_far`
- 신규 코드의 `failure_check_name()` 매핑

### 5.3 실측 재검증 — 프로젝트 최초의 정당한 `verified`

수정 후 `--repair-existing`으로 재실행했다(영수증 `20260729_101244_970_5bfec260cf.json`).

```
status          = verified
measured_checks = ['gameplay', 'movement', 'bidirectional', 'jump', 'components:Player']
skipped_checks  = []
failures        = []
```

| 사이클 | 실패 |
|---|---|
| verify 1 | `player_moved_too_far`, `d_moved_too_far`, `a_moved_too_far` |
| reverify 2 | **없음 → verified** |

**v1.11.2 §7이 다음 사이클의 목표로 제시한 "`measured_checks`가 채워진 첫 번째 정당한
검증 통과"를 달성했다.** 이전까지 이 프로젝트의 `verified` 영수증 3건은 전부
Play Mode를 돌리지 않은 공집합 성공이었다.

**측정값 대조**

| 항목 | v1.11.3 실행 | v1.11.4 실행 |
|---|---|---|
| D 이동 (1초) | 126.78 (통과) | **5.00** |
| A 이동 (1초) | -131.87 (통과) | **-4.91** |
| 점프 최고점 Y | 1.10 (미상승) | **6.07** |
| `player_did_not_move_right` | 발생 (거짓 실패) | **없음** |
| 최종 판정 | failed | **verified** |

두 수정이 모두 실전에서 확인됐다.

1. **거짓 실패 해소** — A/D를 쓰게 되어 `player_did_not_move_right`가 사라졌다.
2. **거짓 통과 차단** — 이전에 통과하던 126~131유닛 폭주를 1차 검증이 즉시 잡았고,
   repair가 이를 실제로 고쳤다.

**모델이 수행한 수정** (`PlayerMovement.cs`) — 호스트 지침이 의도대로 작동했다.

```csharp
// 폭주 물리 수정: 누적 Impulse → 속도 직접 설정 + 상한
Vector3 targetVelocity = new Vector3(moveInput * moveSpeed, rb.linearVelocity.y, 0);
rb.linearVelocity = Vector3.ClampMagnitude(targetVelocity, moveSpeed);

// 접지 판정 수정: groundLayer 설정 + Collider.bounds 기반 레이캐스트
groundLayer = LayerMask.GetMask("Default");
float raycastDistance = capsule.height * 0.5f + 0.1f;
```

`fix_prompt()`에 추가한 "지속 입력은 `linearVelocity`를 직접 설정하고 최대 속도를
제한하라"는 지침을 모델이 그대로 따랐다.

## 6. 남은 과제

1. **repair snapshot/rollback** (v1.11.3 §6에서 실측 근거 확보, 최우선 이월):
   최선 사이클의 산출물을 보존하고 회귀 사이클을 원자적으로 되돌린다.
2. **repair 반복 효율**: v1.11.3 실행에서 3개 사이클 모두 `FIX_MAX_ITERS=20`을
   소진했다. repair 프롬프트가 실패 항목에 더 좁게 집중하도록 개선할 여지가 있다.
3. **점프 키 명세**: 이동은 요청의 키를 따르게 했지만 점프는 여전히 `space` 고정이다.
   다른 점프 키를 요청하면 같은 종류의 거짓 실패가 난다.
