# v1.11.10 — 접지 게이트 오탐 제거 · 차단 메시지에 코드 첨부

작성일: 2026-07-29
대상 버전: **v1.11.10**
선행 문서: [v1.11.9](v1.11.9_bounded_jump_and_unrewritten_scripts.md)

## 1. 배경

v1.11.9는 점프 물리를 고쳤지만(`+19.96` → `+4.98`, 착지 true) `build_stage_success`가
`true`에서 `false`로 후퇴했다. 빌더가 `unity_write_script`를 14회 시도해 한 번도
통과하지 못하고 iteration 한도에 닿았기 때문이다.

v1.11.9 문서는 이를 "예산 문제"로 적었다. 실행 로그
`20260729_154516_207_...jsonl`을 끝까지 보면 **오진이었다.**

### 1.1 실제로 일어난 일

14회의 차단 사유가 두 구간으로 갈린다.

| 시도 | 파일명 | 길이 | 차단 사유 |
|---:|---|---:|---|
| 1 | PlayerMovement.cs | 2090 | `Collider.bounds or Ground collision check` |
| 2–5 | PlayerMovement.cs | ~1850 | 〃 (동일, 4회 반복) |
| 6 | PlayerController.cs | 1835 | 〃 |
| 7 | SimplePlayerController.cs | 1135 | 9개 항목 전부 |
| 8 | BasePlayer.cs | **271** | 9개 항목 전부 |
| 9–14 | PlayerBasic / PlayerMovementSimple / TestPlayer / BasicMovement / PlayerController / PlayerMovementLegacy | 453~1168 | 9개 항목 전부 |
| 15 (repair) | PlayerMovement.cs | 1808 | **통과** |

1~5회차는 **빠진 항목이 딱 하나**였다. rising edge를 포함한 나머지는 전부 맞았다.
그 하나가 접지 검사였고, 5회차의 구현은 이랬다.

```csharp
void CheckGrounded() {
    RaycastHit hit;
    if (Physics.Raycast(transform.position, Vector3.down, out hit, 1.5f)) isGrounded = true;
    else isGrounded = false;
}
```

**정상 동작하는 코드다.** 캡슐이 y≈1.1에 있고 1.5유닛 아래로 쏘면 바닥에 닿는다.
LayerMask도 인스펙터 의존도 없다. 게이트가 막은 이유는 오직 문자열 `.bounds`가 없고
`OnCollision*` 메서드가 없어서였다. **결함이 아니라 철자를 검사한 것이다.**

6회차부터 모델이 게이트를 회피하기 시작했다. 파일명을 계속 바꾸고(`PlayerController` →
`SimplePlayerController` → `BasePlayer` → … → `PlayerMovementLegacy`) 내용을 2090자에서
271자까지 줄이며 `using UnityEngine.InputSystem`까지 버렸다. 게이트는 버텼지만 그 사이
예산 8회가 사라졌다.

### 1.2 대조 증거

같은 모델, 같은 실행에서 repair 단계는 **한 번에 통과**했다. 차이는 안내의 형태다.

| | 안내 형태 | 결과 |
|---|---|---|
| 빌더 게이트 | `Missing: Collider.bounds or Ground collision check` (라벨) | 14회 실패 |
| repair `fix_prompt` | 고쳐야 할 코드를 직접 제시 | 1회 성공 |

라벨은 무엇이 없는지 말하지만 무엇을 쓸지 말하지 않는다.

## 2. 변경 내용

### 2.1 접지 검사를 철자에서 결함 조건으로

`_grounding_gaps()`가 판정 기준을 뒤집었다. 이제 **막을 수 없는 형태만 막는다.**

허용: `Physics.Raycast` / `CheckSphere` / `CheckBox` / `OverlapSphere` / `SphereCast` /
`BoxCast` / `OnCollision*` 노멀 / `.bounds` 기반 — 자기 완결적이면 형태를 가리지 않는다.

차단:

1. 접지 검사가 **아예 없음**
2. 접지 검사가 **코드가 대입하지 않는 인스펙터 필드에 의존**함
   - `public LayerMask groundLayer;` → 값 0 → 어떤 레이어에도 안 맞음 (1회차의 실제 결함)
   - `public Transform groundCheck;` → null → NRE

코드 안에서 대입되거나(`= ~0`) null/value 가드가 있으면 통과시킨다.

v1.11.7이 `.bounds`를 요구한 원래 이유는 "레이 거리가 콜라이더에 못 닿음"이었는데, 그건
거리 문제지 철자 문제가 아니다. 정적으로 증명 가능한 죽은 코드만 게이트가 막고, 실제
동작은 검증 계층이 판정한다 — 이 분담이 원칙이다.

### 2.2 차단 메시지에 코드 첨부

`_input_script_block_message()`가 세 가지를 한다.

1. 빠진 항목 **전체**를 짧은 라벨로 나열한다(모델이 전체 그림을 보게).
2. 앞의 **두 항목에 대해 정확한 코드**를 붙인다(`_GAP_REMEDIES`).
3. 같은 요청에서 2회 이상 차단되면 경고를 추가한다 — **"파일명을 바꾸거나 단순화해도
   같은 정책이 적용된다. 첫 항목만 고치고 나머지는 그대로 두라."**

3번은 6~14회차의 rename 회피에 8회를 쓴 것에 대한 직접 대응이다.

#### 1차에서 드러난 것 — 게이트가 `Update` 본문만 읽었다

3~5회차가 `void Update() { HandleInput(); CheckGrounded(); }` 형태로 썼다. 정상적인,
오히려 더 잘 구조화된 코드인데 게이트가 헬퍼를 따라가지 않아 래치 전체를 누락으로
판정했다. `.bounds`와 같은 계열의 오탐이다. `_frame_body()`가 Update/FixedUpdate가
호출하는 헬퍼 본문까지 합쳐 보도록 고쳤다.

#### 2차에서 드러난 것 — remedy가 결함을 가르치고 있었다

2차가 쓴 스크립트는 1차에서 통과한 것과 **바이트 동일**(sha `2f1cf9c5`)한데 결과가
갈렸다. 변수는 스크립트가 아니라 씬이었다.

| | 1차 (통과) | 2차 (실패) |
|---|---|---|
| Floor | y=0, scale.y=0.2 → 윗면 0.1 | y=−1 → 윗면 −0.9 |
| Player | y=1 | y=0 |
| `GroundCheck` 자식 | 빌더가 **[0,−1,0]에 생성** | 생성 안 함 |

스크립트의 접지 지점 공식 `-capsule.height/2 + capsule.radius`는 −0.5인데 기본 캡슐의
바닥 끝은 −1.0이다. 그 지점은 캡슐 안쪽이고 `groundCheckDistance = 0.1`로는 바닥에
닿지 않는다. **이 접지 검사는 두 실행 모두에서 고장나 있었다.** 1차가 통과한 것은 씬에
−1.0짜리 `GroundCheck` 오브젝트가 있어 스크립트의 "없을 때만 생성" 분기가 실행되지
않았기 때문이다. 1차의 성공은 운이었다.

그리고 이 잘못된 공식은 **§2.2에서 이 문서의 작성자가 remedy 스니펫에 넣은 것**이다.
1차가 통과했다는 이유로 repair 출력의 공식을 검증 없이 가져다 썼다. remedy가 예방하려는
결함을 remedy가 되풀이하고 있었다.

교체한 형태는 자식 오브젝트도 씬 배치 가정도 필요 없다.

```csharp
var col = GetComponent<Collider>();
isGrounded = Physics.Raycast(col.bounds.center, Vector3.down, col.bounds.extents.y + 0.15f);
```

추측한 오프셋으로 자식 접지 지점을 만들지 말라는 경고를 함께 넣었고, remedy 스니펫이
`localPosition` 오프셋을 가르치지 않는지 검사하는 테스트를 추가했다.

#### 2차에서 드러난 것 — 무의미한 재작성

repair가 동일한 3322바이트 파일을 **5회** 썼고(해시 전부 동일) `no_verification_progress`로
끝났다. 이미 디스크에 있는 내용과 바이트 동일한 `unity_write_script`는 검증 결과를 바꿀 수
없으므로 차단하고, 실패가 이 코드에 그대로 있으니 구현을 바꾸라고 알린다.

#### 3차가 운이 아닌 근거

- 씬 배치가 1·2차와 또 달랐다(Floor y=−0.5 scale.y=1 → 윗면 0, Player y=1).
- 이번엔 `GroundCheck` 자식 오브젝트를 만들지 않았다.
- 접지가 `col.bounds` 기반 + 충돌 노멀 이중이라 씬 배치에 의존하지 않는다.
- write 2회 중 1회차 차단은 실제 결함(미대입 `LayerMask`)이었고 2회차가 통과했다.
- repair 사이클이 **0회**다. 빌더 산출물이 첫 독립 검증을 그대로 통과했다.

#### 한계

- **n=1이다.** 세 실행의 씬 배치가 매번 달랐던 것에서 보듯 실행 간 분산이 크다.
  통과 1회는 안정성의 증거가 아니다.
- 모델이 remedy 스니펫의 코드를 상당히 그대로 채용했다. 이 E2E가 측정하는 것은
  "주어진 지침을 정확히 적용하는 능력"이며, "스스로 고안하는 능력"보다 약한 주장이다.
  출력 바이트를 고쳐 쓰는 대필과는 층위가 다르지만, 영수증의 의미를 읽을 때 구분해야 한다.
- `motion_deltas`에 Z 성분(+0.16 / −0.13)과 Y 드리프트(−0.40)가 있다. Rigidbody 회전을
  고정하지 않아 캡슐이 약간 기운다. 요청된 검사 항목은 아니다.

## 5. 남은 과제

1. **통과의 재현성 확인**: 3차 통과는 n=1이다. 같은 프롬프트를 새 씬 경로로 여러 번
   돌려 `build_stage_success=true`가 안정적인지 봐야 한다.
2. remedy 스니펫 채용 비중을 낮출지 검토. 지금 E2E는 "지침을 정확히 적용하는 능력"을
   측정한다. 완성 스크립트 전체를 주는 방향은 반대로 가는 것이므로 피한다.
3. Rigidbody 회전 고정을 요청하지 않은 씬의 Z/회전 드리프트를 검증 명세에 넣을지 검토.
4. 점프 상한 10.0의 저중력 씬 오탐 여부.
5. 브리지 도메인 리로드·held-key 재큐잉의 Unity 통합 회귀 테스트.
