# v1.12.0 — 긴 명령이 끝까지 가지 못한 이유는 호스트 규칙끼리의 충돌이었다

"플랫포머 한 스테이지를 만들어줘" 같은 긴 명령이 완주하지 못한다. 원인을 찾으러
기준선을 돌렸더니 **계획 기계는 켜지지도 않았고**, 예산은 서로 모순되는 호스트 규칙
둘을 오가며 타고 있었다.

> **로그 날짜 주의.** 이 세션 도중 시스템 시계가 `2026-08-06`에서 `2026-08-09`로
> 맞춰졌다. 같은 세션의 증거가 `logs/*/2026/08/06/`과 `.../08/09/` 두 곳에 나뉘어
> 있다. 인용한 경로는 실제 경로 그대로다.

## 1. 배경 — 계획 기계의 기록

`planner.py`는 큰 요청을 마일스톤으로 쪼갠다. 기록된 plan 모드 15회를 세면:

```text
계획된 마일스톤 71개 중   시작 32개(45%)   완료 18개(25%)
계획 전면 중단            15회 중 11회 (73%)
마일스톤 종료 사유        성공 18 · 이터레이션 한도 10 · 산출물 누락 1
한도를 친 10건 중 산출물까지 완성된 것: 1건
```

[agent.py:1674](../agent.py)가 마일스톤 하나가 최종 실패하면 `break`로 계획 전체를
버린다. 그래서 39개는 시작조차 못 했다.

**그런데 기준선을 돌려 보니 이 경로는 발동하지도 않았다.**

## 3. 세 가지를 고쳤다

### 3.1 게이트가 "모델이 쓴 것"을 지목한다

첫 기준선의 예산 30회 중 **17회가 거부**였고, 입력 게이트 차단 21회 중 **15회가 같은
항목**(`Rigidbody.linearVelocity`)이었다. 그 실행의 스크립트 쓰기 24회를 세면 —

```text
rb.velocity      17회
linearVelocity    7회
```

Unity 6이 `velocity`를 `linearVelocity`로 바꿨는데 모델의 학습 데이터가 그 이전이라
옛 이름으로 수렴한다. 게이트는 "Missing: Rigidbody.linearVelocity"라고만 말해서
**"네가 쓴 것을 고쳐라"가 전달되지 않았다.**

```text
Missing: Rigidbody.linearVelocity — you wrote `.velocity`, which Unity 6 renamed.
Rename every `.velocity` to `.linearVelocity`; nothing else about the line changes.
```

`.velocity`가 없는 스크립트는 예전 문구 그대로다.

### 3.2 `policy_lint`와 `task_contract`가 서로 다른 것을 요구하고 있었다

두 번째 기준선에서 `.velocity` 루프는 사라졌지만(차단 21 → 1) **다른 비수렴 루프가
그 자리를 차지했다.** `policy_lint:keyboard_null_check_missing`이 repair 3사이클을
그대로 통과했다.

```python
# policy_lint — 문자 그대로의 형태만 인정했다
re.search(r"Keyboard\.current\s*(?:==\s*null|is\s+null)", code)
```

```csharp
// 모델이 쓴 것 — 그리고 task_contract의 교정 스니펫이 가르치는 바로 그 형태
var keyboard = Keyboard.current;
if (keyboard == null) return;
```

**게이트가 A를 가르치고 린트가 B를 요구한다.** 모델이 안내를 정확히 따를수록 린트에
걸리고, repair는 영원히 수렴하지 못한다. 그리고 `policy_lint` 위반 하나가 E3로
gameplay·movement·jump·boost·camera·screenshot을 전부 blocked시킨다 — 앞의 두
기준선에서 11개가 미측정으로 남은 이유다.

지역 변수를 거치는 형태·역방향 비교·`is null`·타입 선언을 모두 인정하게 했다.
**검사가 아예 없는 스크립트는 여전히 걸린다.**

### 3.3 계획 강등에 이유가 남는다

`make_plan`의 실패 경로 넷 중 **모델이 `mode: "single"`을 고르는 경로만 조용했다.**
그래서 "큰 요청으로 판단해 계획을 세웁니다"를 찍고도 계획 없이 돈 것을 사후에 알
방법이 없었다.

```text
model_chose_single     모델이 단일 작업으로 판단
pruned_below_minimum   레벨 단계를 걷어내니 마일스톤이 2개 미만
invalid_plan_json      계획 JSON이 두 번 다 유효하지 않음
planner_call_failed    플래닝 호출 자체가 실패
```

`execution_mode` 이벤트에 `planning_attempted`·`degraded_reason`을 함께 싣는다.

## 4. 검증

### 4.1 실측

§2의 표. 세 번째 실행에서 `skipped_checks`가 **11 → 0**이 됐다.

### 4.2 단위 테스트

**309 → 316건**, subtest 48 → 52건. 전부 통과.

- 옛 `.velocity`를 쓴 스크립트는 이름을 지목당하고, 안 쓴 스크립트는 예전 문구
- 게이트가 가르치는 null 검사 형태 넷이 린트를 통과하고, 검사 없는 것은 여전히 걸림
- 계획 강등 세 경로(모델 opt-out · 잘못된 JSON · 정상 계획)가 이유를 남김

### 4.3 측정하지 않은 것

- **각 조건이 1회씩이다.** `.velocity` 지목의 효과(거부 17 → 1)는 크지만 모델
  편차일 가능성을 배제할 수 없다
- **긴 명령은 여전히 실패한다.** 세 번째 실행은 측정까지 갔을 뿐 게임이 동작하지
  않았다 — `d` 이동이 +0.055, 점프 0. **결함이 blocked 뒤에 가려져 있다가 이제
  보이게 된 것**이고, 고친 것이 아니다
- **모델이 계획을 두 번 다 거부했다**(2/2). 왜 그러는지는 아직 안 봤다
- 마일스톤 실패 시 계획 전면 중단(§1)은 **손대지 않았다.** 계획이 켜지지 않는 한
  그 경로는 발동하지 않는다
