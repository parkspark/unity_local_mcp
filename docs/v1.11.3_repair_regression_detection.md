## 1. 배경 — 실측 E2E에서 발견

v1.11.2 완료 후 **실제 로컬 모델(`qwen3-coder:30b`)로 첫 E2E 재검증**을 실행했다.

요청: "Assets/Scenes/SampleScene.unity 씬에 Player(캡슐)를 만들고 A/D 좌우 이동과
Space 점프가 되도록 구현해줘. (…) 이동과 점프가 실제로 되는지 검증까지 끝내줘."

영수증 `20260729_094913_862_fe898db6f5.json`:

```
requested_checks = ['gameplay', 'movement', 'bidirectional', 'jump', 'components:Player']
measured_checks  = ['gameplay', 'movement', 'bidirectional', 'jump', 'components:Player']
skipped_checks   = []
failures = ['player_did_not_move_right', 'player_did_not_jump', 'verification_regressed']
```

**v1.11.2의 목표는 달성됐다.** 요청한 검증 항목이 전부 실제로 측정됐고
(`skipped_checks` 공집합), 로컬 모델이 Play Mode에 진입해 `unity_send_key`로
입력을 보내고 좌표가 실측됐다. 이 프로젝트 최초의 완전 측정 사례다.

그러나 `verification_regressed`로 **repair가 3회 예산 중 1회 만에 중단**됐다.

## 2. 결함 1 — 최초 측정을 회귀로 오판

### 증거

실행 로그(JSONL)의 사이클 1 델타:

```
resolved   = ['blocked:jump:compile_not_ready', 'blocked:movement:scene_not_ready',
              'compile_errors:1', 'component_missing:Player:Rigidbody',
              'scene_not_saved', ...(21건)]
introduced = ['player_did_not_jump', 'player_did_not_move_right']
→ verification_regression_stop
```

### 원인

[agent.py](../agent.py)의 회귀 감지가 **집합 차집합만** 사용했다.

```python
introduced = current_failures - previous_failures
critical_new = [i for i in introduced if i.startswith(critical_prefixes)]
if critical_new: → verification_regressed → break
```

1차 검증 시점의 실패는 전부 `blocked:*`, `compile_errors:1`,
`component_missing:Player:Rigidbody` 같은 **"아직 측정조차 못 한" 차단 상태**였다.
repair가 컴파일·Rigidbody·씬 저장을 고쳐 **처음으로 게임플레이 측정이 가능해진 순간**,
그 최초 실측 결과가 "새로 생긴 실패"로 잡혀 회귀로 오판됐다.

이건 진짜 회귀(통과하던 것이 깨짐)가 아니라 **최초 측정**이다. 결과적으로 모델은
실제 게임플레이 버그를 고칠 기회를 받지 못하고 강제 종료됐다.

### 수정

v1.11.2에서 도입한 `measured_checks()`를 회귀 판정의 기준으로 재사용한다.
실패 코드가 어느 검사에 속하는지 매핑하고, **이전 사이클에 측정되지 않았던 검사의
실패는 회귀가 아니라 최초 측정**으로 분류한다.

```python
check = failure_check_name(item)
if check is not None and check not in previous_measured:
    first_measurements.append(item)   # 회귀 아님 — repair가 고쳐야 할 대상
else:
    critical_new.append(item)         # 진짜 회귀
```

`failure_check_name()`이 `None`을 반환하는 코드(`scene_not_saved`, `compile_errors:`,
`asset_missing:`, `wrong_active_scene:`)는 차단될 수 없는 정적 검사이므로 새로 나타나면
언제나 회귀로 취급한다.

## 3. 결함 2 — 오류 개수 감소를 회귀로 오판

같은 블록에서 발견한 별개의 버그다. `compile_errors:N`은 개수가 문자열에 포함되므로,

```
previous = {'compile_errors:3'}
current  = {'compile_errors:1'}
introduced = {'compile_errors:1'}   ← 문자열이 다르므로 "새 실패"
→ verification_regressed
```

**컴파일 오류가 3건에서 1건으로 줄어든 것이 회귀로 판정**된다. repair가 진전을 만들수록
중단될 확률이 올라가는 역설적 구조였다.

### 수정

개수를 갖는 실패 코드를 숫자로 비교한다. 개수가 **증가**할 때만 회귀다.

```python
counted = failure_count(item)          # "compile_errors:3" → ("compile_errors", 3)
if counted is not None:
    head, count = counted
    before = previous_counts.get(head)
    if before is not None and count <= before:
        improved_counts.append(item)   # 진전 — 회귀 아님
        continue
```

## 5. 검증

### 5.1 자동 테스트

| 지표 | v1.11.2 | v1.11.3 |
|---|---:|---:|
| 테스트 수 | 101 | **108** (+3 subtests) |
| 결과 | 101 passed | **108 passed** |

신규 테스트(`RegressionDetectionTests`)는 실측 E2E 시나리오를 그대로 고정한다.

- 차단 해제 후 최초 측정 실패 → 중단하지 않고 repair 2회 진행
- 통과하던 검사가 깨지면 → 여전히 회귀로 중단
- 컴파일 오류 3→1 → 진전으로 인정
- 컴파일 오류 1→5 → 회귀로 중단
- 새로 깨진 정적 검사(`scene_not_saved`) → 회귀로 중단
- `failure_check_name()` / `failure_count()` 매핑 정확성

### 5.2 실측 재검증

수정 후 동일 프로젝트에 `--repair-existing`으로 재실행했다(영수증
`20260729_100359_216_4bf6dfd4a8.json`). 이전 실행이 남긴 실제 게임플레이 버그
2건이 검증 대상이다.

| 사이클 | 실패 | 델타 |
|---|---|---|
| verify 1 | 2건 (이동, 점프) | — |
| reverify 2 | 2건 | 변화 없음 |
| reverify 3 | **1건** (이동) | **`player_did_not_jump` 해결** |
| reverify 4 | 3건 | `player_did_not_jump` 재발 → `verification_regressed` |

**수정 전후 대조**

| | v1.11.2 | v1.11.3 |
|---|---|---|
| 사용한 repair 사이클 | 1 / 3 (조기 중단) | **3 / 3 (완주)** |
| 중단 사유 | 최초 측정을 회귀로 오판 | 실제 회귀 감지 |
| repair의 실질 성과 | 없음 | **점프 버그 실제 수정(사이클 2)** |

세 가지가 모두 확인됐다.

1. **거짓 회귀가 사라졌다** — 사이클 1의 `persisted`(변화 없음)에서 중단하지 않았다.
2. **repair가 실제로 작동한다** — 사이클 2에서 점프 버그를 스스로 고쳤다.
   `first_measurements`/`improved_counts`가 빈 채로 정상 진행된 것도 확인된다.
3. **진짜 회귀는 여전히 잡는다** — 사이클 3에서 이동을 고치려다 통과하던 점프를
   깨뜨리자, `jump`가 `previous_measured`에 있으므로 정확히 회귀로 분류하고 중단했다.

## 6. 이 실행이 증명한 rollback의 필요성

사이클 3 시점의 상태(실패 1건)가 최종 상태(실패 2건)보다 **엄격히 낫다.** 그런데
rollback이 없어 프로젝트는 더 나쁜 마지막 상태로 남는다.

```
verify 1:   2건  ─┐
reverify 3: 1건  ─┤ ← 최선 상태. 여기로 되돌려야 한다.
reverify 4: 2건  ─┘ ← 실제로 남은 상태
```

회귀 *판정*은 이제 정확하지만 회귀 *복구*는 없다. 다음 P1(snapshot/rollback)이
필요한 이유가 추측이 아니라 실측으로 확인됐다: **최선 사이클의 산출물을 보존하고
회귀 사이클을 되돌리면 이 실행은 실패 1건으로 끝났을 것이다.**

## 7. 함께 확인된 게임플레이 버그 (모델 산출물)

호스트 결함과 별개로, 로컬 모델이 생성한 `PlayerMovement.cs`에서 실제 버그 3개를
확인했다. 이는 호스트가 고칠 대상이 아니라 **repair 루프가 고쳐야 할 대상**이다.

| 증상 | 원인 |
|---|---|
| `player_did_not_move_right` | 검증은 `rightArrow`로 테스트하는데 스크립트는 `aKey`/`dKey`만 읽음 |
| `player_did_not_jump` | `groundLayer`(LayerMask)가 미설정(기본값 0) → `Physics.Raycast` 접지 판정이 항상 실패 → `isGrounded` 게이트에 막힘 |
| D/A 이동 131유닛 (이상값) | `AddForce(..., ForceMode.Impulse)`를 매 `FixedUpdate`마다 호출해 속도 폭주. 현재 양방향 검사는 하한(2.0)만 보고 **상한이 없어 통과** |

세 번째는 검증 로직의 공백이기도 하다 — 물리적으로 비정상인 이동을 통과시킨다.
§7의 후속 과제로 남긴다.

## 8. 남은 과제

1. **repair snapshot/rollback** (최우선, §6에서 실측으로 근거 확보): 최선 사이클의
   산출물을 보존하고 회귀 사이클을 원자적으로 되돌린다.
2. **이동 거리 상한 검사**: `require_bidirectional`/`require_movement`에 상한을 도입해
   Impulse 폭주 같은 비정상 물리를 잡는다. 현재 D/A 이동 126~131유닛이 통과한다.
3. **입력 키 명세 일치**: 요청은 A/D인데 `require_movement`는 `rightArrow`로 테스트한다.
   요청에 명시된 키를 검증이 우선 사용하도록 명세 추출을 확장한다.
   이번 실행의 `player_did_not_move_right`는 이 불일치가 원인일 가능성이 높다.
4. **repair 반복 효율**: 3개 사이클 모두 `tool-call iteration limit reached`
   (`FIX_MAX_ITERS=20` 소진)로 끝났다. repair 프롬프트가 실패 항목에 더 좁게
   집중하도록 개선할 여지가 있다.
