# v1.12.7 — 올바른 복사본이 잘못된 부착을 가렸다

장문 플랫포머 프롬프트를 같은 조건으로 5회 더 실행했다. `verified`는 **2/5**,
`build_stage_success`는 **0/5**였다. 마지막 회차에서 빌더가
`SideScrollerCamera`를 Main Camera뿐 아니라 **Player에도 붙였다.** 기존 필수 컴포넌트
검사는 올바른 대상에 컴포넌트가 있는지만 봤기 때문에 이 상태를 통과시켰고, Player에
붙은 복사본은 자기 자신의 Transform을 추종해 위치를 매 프레임 더했다. Player는
Y 수백·Z 음수 수천 유닛으로 폭주했고 요청된 17개 검사 중 9개가 측정되지 않았다.

---

## 1. 배경 — 존재 검사는 중복 오부착을 보지 못했다

실패 영수증 `20260818_102747_183_78d54060c3`의 정적 구성은 다음과 같다.

```text
Player      Rigidbody, Collider, PlayerMovement25D, SideScrollerCamera
Main Camera Camera, SideScrollerCamera
```

요청은 `PlayerMovement25D`를 Player에, `SideScrollerCamera`를 Main Camera에 배정했다.
그러나 이전 검사는 각 대상에 **필수 컴포넌트가 하나라도 있으면** 통과했다. Main Camera의
구성이 맞았으므로 Player의 잘못된 복사본은 실패가 아니었다.

그 결과 Play Mode에서 Player 위치가 다음처럼 증가했다.

```text
(0, 39.829, -197.5)
(0, 70.793, -357.5)
(0, 101.282, -517.5)
...
```

카메라 스크립트의 target도 Player였고 컴포넌트가 붙은 대상도 Player였으므로,
`target.position + offset`을 다시 Player.position에 대입하는 자기 추종 루프였다.
repair는 Main Camera에 같은 스크립트를 추가하고 target을 연결했지만, **Player 쪽
복사본을 제거하라는 실패가 없어서** 세 사이클 동안 원인이 남았다.

## 2. 변경 내용

### 2.1 `component_misplaced` 실패

요청의 `required_components`가 특정 핵심 오브젝트에 배정한 **사용자 스크립트**를 다른
핵심 오브젝트에서도 관측하면 다음 실패를 낸다.

```text
component_misplaced:Player:SideScrollerCamera:expected:Main Camera
```

Collider·Rigidbody·Camera 같은 Unity 내장 컴포넌트는 여러 오브젝트에 함께 있을 수
있으므로 이 검사에서 제외한다. 사용자 스크립트만 대상이다.

### 2.2 Play Mode 이전 차단

오부착은 정적 구성 조회 직후 검사한다. 하나라도 있으면 gameplay·movement·jump·boost·
camera·screenshot 단계를 Play Mode 진입 전에 차단한다. 자기 추종처럼 런타임 상태를
폭주시켜 뒤의 측정까지 무효화하는 결함을 먼저 고치게 한다.

### 2.3 실제 대상 이름을 포함한 repair 안내

repair 프롬프트는 잘못된 대상·컴포넌트·올바른 대상을 그대로 제공한다.

```text
unity_remove_component(
    target="Player",
    component_type="SideScrollerCamera",
    remove_all=true,
)
```

올바른 Main Camera의 복사본은 유지하고, 오브젝트를 삭제하거나 재생성하지 말라고 함께
명시한다.

## 3. 검증

### 3.1 수정 전 장문 E2E 5회

모든 회차는 로컬 모델 `qwen3-coder:30b`가 다음 명령 형태로 직접 도구를 호출했다.

```bash
uv run python main.py --project "C:\Users\park\My project (60)" --prompt-file <파일>
```

| 회차 | 영수증 | 판정 | 실측/미측정 | attempts | 마지막 실패 |
|---|---|---:|---:|---:|---|
| repro16 | `20260818_101345_142_f6d347e0e9` | failed | 17/0 | 4 | `boost_distance_too_short` |
| repro17 | `20260818_101735_733_357729c455` | failed | 17/0 | 4 | 이동 경로·점프·착지·부스트 4건 |
| repro18 | `20260818_102119_231_b53da49974` | verified | 17/0 | 3 | 없음 |
| repro19 | `20260818_102412_200_775e966519` | verified | 17/0 | 2 | 없음 |
| repro20 | `20260818_102747_183_78d54060c3` | failed | 8/9 | 4 | 런타임·이동·점프·카메라·부스트 미측정 |

합계는 **`verified` 2/5, 17개 검사 완전 측정 4/5, `build_stage_success` 0/5**다.
다섯 회차 모두 `unmapped_requirements` 2건(플랫폼 5개 이상, 낙사 복귀)이 남으므로,
`verified`는 요청 전체가 아니라 측정된 17개 검사에 대한 판정이다.

### 3.2 수정 후 실제 결함의 repair-existing

repro20의 잘못된 씬을 그대로 두고 로컬 모델에 다시 맡겼다.

```bash
uv run python main.py --project "C:\Users\park\My project (60)" \
  --prompt-file prompts/v112_repro20.txt --repair-existing
```

영수증: `20260818_103258_514_22e91f63b9`

| 시도 | 호스트 판정 | 로컬 모델의 다음 수정 |
|---:|---|---|
| 1 | `component_misplaced:Player:SideScrollerCamera:expected:Main Camera` | Player의 복사본 1개만 `unity_remove_component`로 제거 |
| 2 | `player_fell_no_ground_in_scene` | Ground 생성·저장 |
| 3 | 양방향 `boost_distance_too_short` | 이동 스크립트의 부스트 처리 수정 |
| 4 | 실패 없음 | `verified` |

최종 구성에는 Player의 `SideScrollerCamera`가 없고 Main Camera의 복사본만 남았다.
결과는 **요청 17개·실측 17개·미측정 0·`verified`**다.
`--repair-existing`은 빌더 단계를 생략하므로 이 영수증의 `build_stage_success`는
의도대로 `null`이다.

수정 후 새 씬 빌더 반복은 실행하지 않았다. 따라서 이번 실측은 **오부착 검출·Play Mode
전 차단·로컬 모델 제거·후속 검증 수렴**을 증명하며, 빌더가 처음부터 오부착하지 않는
비율이나 장문 요청의 새 재현성 수치를 증명하지 않는다.

### 3.3 단위 테스트

전체 테스트는 **369 → 372개**, subtest는 **71개 유지**로 전부 통과했다. 추가한 3개는
오부착 실패와 검사 매핑, 내장 컴포넌트 중복의 비오탐, 잘못된 복사본만 제거하는 repair
안내를 고정한다.
