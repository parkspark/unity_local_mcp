# v1.11.29 — 접촉이 성립하지 않은 채 만들어지는 것을 검사로

A0의 표본이 안 쌓이는 이유는 둘이었다. 측정 쪽은 v1.11.28이 닫았고, 남은 빌더 쪽 둘을
여기서 처리한다 — **트리거를 안 만들거나(A4), 트리거에 Rigidbody를 붙여 아이템이
월드 밖으로 떨어지거나(A5).**

---

## 1. 배경 — 근거는 이미 셌다

v1.11.27이 기록된 실행을 재생해 A4의 크기를 냈다.

```text
OnTriggerEnter를 쓴 실행                 : 30
  그중 요청이 접촉 상호작용인 실행       : 13
  **트리거를 아무 데도 만들지 않은 실행**:  6   (+ 라이브 2건)
    그중 verified로 나간 것              :  2
```

E4가 `RequireComponent`를 기각한 기준(211개 중 211개가 걸려 스타일 규칙이 됨)과 정반대다
— 13건 중 7건이 제대로 만들었으므로 **가르는 축이 실재한다.** A5는 v1.11.28이 실측
2건을 냈다.

## 2. 브리지가 `isTrigger`를 안 내주고 있었다

호스트는 트리거 여부를 볼 수 없었다. `JsonUtility.ToJson`이 엔진 콜라이더에서 아무
필드도 내주지 않아 `data`가 `null`이었다. Rigidbody가 이미 특수 케이스로 처리돼 있어
같은 자리에 콜라이더를 넣었다.

```csharp
if (c is Collider col)
{
    cj["data"] = new JObject { ["isTrigger"] = col.isTrigger, ["enabled"] = col.enabled };
}
```

```json
{"type":"UnityEngine.SphereCollider","data":{"isTrigger":true,"enabled":true}}
```

프로젝트 사본까지 설치하고 재컴파일해 라이브로 확인했다.

## 3. 검사 둘

### 3.1 `trigger_handler_without_trigger_collider`

**요청 어휘가 아니라 빌더가 실제로 쓴 코드를 근거로 삼는다.** 세션 스크립트가
`OnTriggerEnter`를 정의하고 그것이 참여자에 붙어 있는데, **관측된 참여자 전원이
트리거가 아니라고 확인된** 경우에만 실패다.

- 하나라도 트리거이면 넘어간다 — `OnTriggerEnter`는 둘 중 하나만 트리거여도 발동한다
- 하나라도 판별이 안 되면 넘어간다 — 구버전 브리지 응답을 근거로 실패시키지 않는다
- `OnCollisionEnter`로 구현한 정상적인 획득은 걸리지 않는다

**핸들러는 양쪽 어디에나 있을 수 있다.** 첫 구현은 접촉 후보만 훑었는데, 걸린 6건 중
**4건이 핸들러를 `PlayerMovement.cs`에** 두고 있었다. 라이브에서 실제로 하나 놓쳤고
(§4.2), 참여자에 플레이어를 포함하도록 넓혔다.

### 3.2 `contact_object_fell_away`

**원인이 아니라 결과를 잰다.** 접촉 대상이 시작 높이보다 10 이상 내려갔는가. 트리거와
Rigidbody의 조합을 몰라도 잡히고, 스크립트가 없는 구조물(`Ground`·`Floor`)은 제외한다.

문턱 10은 관측된 낙하(한 표본 만에 −9, 최종 −45)보다 훨씬 낮고 수직으로 움직이는
발판보다 높다.

### 3.3 빌더 안내

검사는 이미 난 결함을 잡을 뿐이다. 예방 쪽도 함께 넣었다 — 트리거를 대상 콜라이더에
설정할 것(플레이어 쪽은 아님), 획득 아이템에 Rigidbody를 붙이지 말 것.

## 4. 검증

### 4.1 오탐 재생 — 기록된 189개 실행

```text
contact_object_fell_away가 걸릴 실행: 3 / 189
  20260806_074736  pickupitem  1.00 → −46.44
  20260806_075229  pickupitem  1.28 → −53.55,  item 1.00 → −47.67
  20260806_075512  item        0.86 → −44.63
```

**셋 다 v1.11.28이 실측으로 확인한 낙하다. 오탐 0.**

### 4.2 라이브 E2E 5회

| 영수증 | 표면 간격 | 사라짐 | 비고 |
|---|---|---|---|
| 090225 | −0.986 | **True** | 첫 시도는 `policy_lint` 차단, repair 후 획득 |
| 090336 | +0.342 | False | **안 닿았다** — 판정할 수 없는 경우 |
| 090542 | −0.999 | **True** | **새 검사 발동 → repair가 트리거 설정 → 획득** |
| 090913 | −0.800 | **True** | 무수정 통과 (`build_stage_success=true`) |
| 091037 | −0.990 | **True** | 무수정 통과 (`build_stage_success=true`) |

**090542가 이 사이클의 핵심이다.** 검출 → 수정 → 측정이 한 실행에서 닫혔다. 그리고
마지막 둘은 검사가 발동할 일 없이 통과했다 — §3.3의 안내가 결함을 만들기 전에 막았다.

`disappeared: true`가 **4/5**다. v1.11.28 이전 10회에서는 0이었다.

### 4.3 A0의 표본이 처음으로 정렬됐다

v1.11.28 이후의 모든 표본이다.

```text
겹침(음수) → 사라짐 :  −1.000  −0.999  −0.990  −0.986  −0.800
겹침(음수) → 안 사라짐: −0.890   ← A5 낙하. 그 자리에 아이템이 없었다
안 닿음(양수) → 안 사라짐: +0.342
```

**부호가 소멸과 정렬하고, 설명되지 않는 표본이 하나도 남지 않았다.** A0이 15건을
모으고도 못 하던 것이다.

**그래도 임계값은 아직 고르지 않았다.** −0.25 ~ 0.0 구간에 표본이 없어 경계가
어디인지 모른다. 비어 있는 것은 안전의 증거가 아니다.

### 4.4 단위 테스트

**287 → 296건**, subtest 48건. 전부 통과.

- 양쪽 어디의 트리거든 충분하다 (대상 쪽 / 플레이어 쪽)
- **핸들러가 플레이어에 있어도 잡는다** (§3.1의 놓친 형태)
- `OnCollisionEnter` 구현은 무고하다
- 콜라이더를 못 본 경우는 판정하지 않는다
- 낙하 문턱, 구조물 제외
- 두 실패가 실패 목록과 repair 안내까지 닿는다

### 4.5 측정하지 않은 것

- **넓힌 검사(플레이어 쪽 핸들러)는 라이브에서 발동한 적이 없다.** 넓힌 뒤의 2회는
  안내가 결함 자체를 막아 검사가 돌 일이 없었다. 단위 테스트로만 확인했다
- **`contact_object_fell_away`도 라이브 발동이 없다.** 재생 3건과 단위 테스트뿐이다
- 임계값 미선정 (§4.3)
- 접촉 후보의 좌표는 여전히 시작 시점 한 번만 찍는다
