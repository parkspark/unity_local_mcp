# Unity Local Agent v1.11.1 진행 현황 및 개선 보고서

작성일: 2026-07-25
대상 버전: **v1.11.1**
저장소: `unity_local_mcp`

## 1. 요약

v1.11.1은 Unity 프로젝트 선택, 브리지 자동 설치·재연결, 컴파일 및 도메인 리로드 진행 상태 표시, 에이전트 계획 실행, 정책 게이트, 독립 검증, 실행 로그와 검증 영수증까지 포함하는 실행 기반으로 발전했다.

호스트 측 단위 테스트와 정적 검증은 안정적이지만, 임의의 Unity 프로젝트를 대상으로 한 전체 E2E 성공까지는 확인되지 않았다. 특히 짧은 자연어 수정 요청에서 검증 조건이 공집합으로 추출되어 실제 Play Mode 측정 없이 `verified`가 될 수 있는 문제가 확인됐다. 따라서 현재 릴리스 판단은 **인프라 릴리스 후보이나 자동 게임 제작·수정 품질은 보완 진행 중**으로 보는 것이 타당하다.

## 2. 현재까지 구현된 범위

- Unity 프로젝트를 CLI, 환경변수, 최근 선택 기록, 기본값 순서로 선택
- 프로젝트 경로 및 Unity 프로젝트 identity 사전 검증
- 브리지 자동 설치, 필수 패키지 보완, 포트 변경 감지 및 재연결
- 컴파일·도메인 리로드·브리지 연결 진행 단계 표시
- Ollama 기반 tool-call 실행 루프와 대형 요청 플래너
- TaskContract 정책 게이트 및 mutation 범위 제한
- 요청별 실행 로그와 전체 MCP 감사 로그
- Unity 씬, 컴파일, 런타임 오류, 컴포넌트, 이동·점프·카메라·부스트·입력 해제의 호스트 측 검증
- 실패 항목만 대상으로 하는 fresh-context repair, 무진전 감지, 새 회귀 감지
- JSON 검증 영수증 및 실패 증거 보존

관련 구현 개요는 [README.md](../README.md)의 파일 구성 및 버전별 개선 사항을 참고한다.

### 3.2 Unity E2E

v1.11.1의 프로젝트 선택 및 연결 UI 변경 이후에는 동일 범위의 전체 Unity E2E 재실행 증거가 아직 없다. 따라서 v1.11.1의 실제 Unity 운용 안정성은 추가 검증이 필요하다.

## 4. 핵심 문제점

### 4.1 검증 공집합 성공 가능성 — 최우선

검증 명세는 `게임` 또는 `플랫포머` 같은 단어가 있어야 gameplay·jump 측정을 활성화한다. 따라서 다음과 같은 요청은 검증 기능은 켜지지만 실제 플레이 조건이 모두 꺼질 수 있다.

> Player가 착지한 뒤 점프가 동작하지 않는다. 수정하고 검증한다.

이 경우 `require_gameplay=false`, `require_jump=false`가 되고 Play Mode를 실행하지 않아도 실패 목록이 비어 `verified`가 될 수 있다. 실제 영수증에도 `verified`이면서 `played=false`인 사례가 남아 있다.

원인은 [verification.py](../verification.py)의 게임 키워드 선행 조건과 [agent.py](../agent.py)의 `실패 목록이 비었는가` 중심 최종 판정이다.

### 4.2 repair가 새 회귀를 만들 수 있음

이전 E2E에서 왼쪽 이동을 고치기 위해 시작 플랫폼을 추가한 뒤 기존 플랫폼 경계에 Player가 겹쳐 오른쪽 이동이 막혔다. 현재 회귀 감지는 작동하지만, 변경 자체를 원자적으로 되돌리는 snapshot/rollback은 부족하다.

### 4.3 외부 경계 코드의 테스트 부족

MCP stdio 연결, 포트 호핑, Unity 창 포커스, 네이티브 모달, CLI 시작·종료는 실제 실패 가능성이 높은데도 자동 테스트 커버리지가 낮거나 없다.

### 4.4 개발 환경에서 기본 테스트 실행이 불편함

`pytest`가 프로젝트 런타임 의존성에 포함되어 있지 않아 별도 임시 의존성 없이는 일반적인 테스트 명령이 실패한다. 개발 의존성과 표준 실행 명령이 필요하다.

### 4.5 v1.11.1 기능 변경과 E2E 증거의 시간 차이

최신 기능은 시작 단계 표시와 프로젝트 연결 편의성에 집중되어 있지만, 현재 보존된 주요 Unity 제작·검증 증거는 주로 v1.10.0 실행에서 나온 것이다. 새 버전 변경이 기존 E2E를 깨뜨리지 않았다는 직접 증명이 부족하다.

## 5. 개선 계획

### P0 — 검증 신뢰성

1. `점프`, `이동`, `착지`, `부스트`, `카메라`를 `게임` 키워드와 독립적으로 감지한다.
2. 행동 검증 조건이 하나라도 추출되면 `require_gameplay=true`로 설정한다.
3. 수정·검증 요청인데 측정 조건이 0개이면 `verified`를 금지하고 `verification_spec_empty`로 종료한다.
4. 짧은 한국어 요청을 포함한 명세 추출 회귀 테스트를 추가한다.
5. 영수증에 `requested_checks`, `measured_checks`, `skipped_checks`를 명시한다.

### P1 — 안전한 자동 repair

1. repair 전 hierarchy, transform, component, 파일 fingerprint를 snapshot한다.
2. 기존에 통과한 조건을 보호 목록으로 고정한다.
3. 레벨 배치 repair는 새 GameObject/Collider 생성을 기본 금지한다.
4. Player 주변 Collider overlap/sweep 검사를 Play 전에 수행한다.
5. 새 P1 회귀가 발생하면 해당 cycle을 자동 rollback한다.
6. 변경 파일·오브젝트·fingerprint를 영수증에 기록한다.

### P1 — v1.11.1 E2E 재검증

격리된 Unity 프로젝트에서 다음 흐름을 한 번에 검증한다.

1. `--project` 선택
2. 브리지 및 패키지 자동 보완
3. 컴파일·도메인 리로드 후 재연결
4. 씬 제작 또는 기존 산출물 repair
5. Play Mode 행동 측정
6. 실패 시 repair와 재검증
7. 입력 해제, Play Mode 종료, 영수증 저장

### P2 — 테스트·개발 경험

- `pytest`, `pytest-cov`를 개발 의존성 그룹으로 선언
- 표준 `test` 및 `coverage` 명령 추가
- `main.py`, `mcp_client.py`, `local_tools.py`, `winfocus.py`, `winmodal.py`의 경계 테스트 추가
- 포트 변경·다중 Unity 창·모달·비정상 종료를 포함한 통합 테스트 추가
- 실행 로그에서 재연결 성공률, repair cycle 수, 검증 누락률을 집계

## 6. 완료 판정 기준

다음 조건을 모두 만족해야 v1.11.1 계열을 안정 릴리스로 판단한다.

- 행동 요청이 공집합 검증으로 `verified`되지 않음
- 검증 명세의 요청 조건과 측정 조건이 영수증에 일치함
- v1.11.1 변경 이후 격리 Unity E2E 1회 이상 완주
- 자동 repair가 새 치명적 회귀를 만들지 않거나 발생 즉시 rollback
- Save Scene 모달, 미해제 입력, 종료되지 않은 Play Mode가 0건
- 브리지 재연결과 프로젝트 identity 검증이 자동 테스트에서 통과

## 7. 결론

v1.11.1은 단순한 Unity tool wrapper를 넘어 실행 정책과 독립 검증을 갖춘 기반으로 발전했다. 현재 가장 위험한 결함은 기능이 실패하는 것보다 **검증 조건이 빠진 요청을 성공으로 판정할 수 있는 것**이다. 따라서 다음 개발 사이클은 기능 확장보다 검증 명세의 강제성, repair rollback, v1.11.1 전체 E2E 재검증을 우선해야 한다.
