# v1.11.20 — 라이브 확인 한 번이 결함 둘을 드러냈다

`docs/STATUS.md` B0(v1.11.19 lint 범위 확대의 라이브 확인)를 재려고 코인 요청을
돌렸다. **확인은 됐고**, 그 과정에서 서로 다른 결함 둘이 함께 나왔다.

---

## 1. B0 — v1.11.19는 라이브에서 작동한다

정리된 프로젝트에 코인 요청을 두 번 돌렸다. 두 번 모두 잡혔다.

```text
1차 (10:14)  policy_lint:undefined_compare_tag:Assets/Scripts/PlayerMovement.cs:Coin
2차 (10:18)  policy_lint:undefined_compare_tag:Assets/Scripts/CoinCollector.cs:Coin
```

2차는 모델이 코인 로직을 별도 파일(`CoinCollector.cs`)로 뺐는데도 잡혔다 —
검사 대상이 요청 문장이 아니라 **세션이 쓴 스크립트 전체**이므로 파일을 나눠도
빠져나가지 못한다.

**8/3에 `verified`로 나갔던 요청이 이제 `failed`가 된다.** 그것이 이 변경의
목적이고, 라이브로 확인됐다.

## 2. 결함 A — 모델 호출 하나가 끊기자 완료된 측정이 사라졌다

1차 실행이 그렇게 끝났다.

```text
verification_finished  outcome: failed
                       policy_lint:undefined_compare_tag:...:Coin  (외 6건)
warning                독립 검증 미통과 7건 — 실패 항목 자동 수정 1/3
model_call_retry       XML syntax error on line 3: unexpected EOF (status code: -1)
exception              ResponseError
run_finished           outcome: error, 56.25초
```

**영수증이 없다.** 검증은 이미 끝났고 실패 목록과 증거가 손에 있었는데, repair
첫 사이클의 Ollama 호출이 끊기면서 예외가 영수증 기록 지점을 건너뛰었다.

`_run_verification_orchestration`은 repair 루프의 `asyncio.TimeoutError`만 잡고
있었다. 다른 예외는 그대로 위로 던져지고, 그 아래에 있는 `write_receipt`가 실행되지
않는다.

### 2.1 크기

기록된 실행 **166건** 중 검증이 끝났는데 영수증이 없는 것은 **4건**이다.

```text
20260729_120124  outcome=error
20260729_142138  outcome=interrupted
20260729_143706  outcome=interrupted
20260805_101424  outcome=error        ← 이번 실행
```

빈도는 낮지만, 잃는 것이 **이 저장소가 존재 이유로 삼는 실측 증거**다.

### 2.2 수정

repair 루프의 모델 호출 실패를 타임아웃과 같은 방식으로 처리한다 —
`repair_aborted:<예외명>`을 실패 목록에 넣고 루프를 빠져나가, **지금까지의 측정이
영수증에 남는다.** 이 표식은 프로젝트 파일의 결함이 아니라 루프 제어 결과이므로
롤백 점수에서 제외한다(`task_time_budget_exhausted`와 같은 취급).

중단(`KeyboardInterrupt`)은 손대지 않았다. 사용자가 멈춘 것이라 예외 처리로
가로채면 Ctrl-C 동작이 바뀐다.

## 3. 결함 B — 롤백이 정책 위반이 남은 상태를 골랐다

2차 실행은 끝까지 갔다(196.8초, `failed`). repair가 **태그 위반을 실제로
고쳤는데**, 롤백이 그것을 되돌렸다.

| 상태 | 미측정 | "실제 결함" | blocked |
|---|---:|---:|---:|
| verify 1 — 태그 위반 있음 | 4 | **2** | 12 |
| reverify — 태그 고쳐짐 | 4 | **5** | 0 |

`_repair_score`는 `(미측정, 실제 결함, blocked)` 순으로 낮은 쪽을 고른다. 미측정이
4로 같으니 실제 결함 2 < 5로 **위반이 남은 쪽**이 이겼다.

그런데 reverify의 "실제 결함" 5건의 정체는 이렇다.

```text
runtime_console_not_checked
player_movement_not_measured
d_movement_not_measured
a_movement_not_measured
player_jump_not_measured
```

**전부 "재지 못했다"이지 결함이 아니다.** 그리고 그 공백은 이미 첫 키
`미측정 = 4`가 세고 있다. 같은 사실을 두 번 센 것이고, 그래서 측정을 시도한 상태가
전부 blocked된 상태보다 나빠 보였다.

바로 그 함수의 주석이 막겠다고 적어 둔 역전이다.

> A blocked state with no observed defects is not better than a state where those
> same checks ran and exposed actionable failures.

### 3.1 수정

실패 코드가 **요청됐지만 측정되지 않은 검사**에 속하면 결함으로 세지 않는다.
판단은 새 규칙이 아니라 이미 있는 `failure_check_name()` 매핑으로 한다.

```python
name = failure_check_name(item)
if name is not None and name in unmeasured_checks:
    continue          # 이미 미측정 키가 세었다
state += 1
```

`runtime_console_not_checked`와 `runtime_wait_missing`은 매핑 표에 없어 결함으로
세어지고 있었다. 둘 다 gameplay 검사의 측정 공백이므로 표에 넣었다.

### 3.2 영향 범위

사이클이 둘 이상인 영수증 **53건**을 재생해 롤백 선택이 바뀌는지 봤다.

**변경 1건 / 유지 52건.** 바뀐 하나가 이 결함을 드러낸 그 실행이다.

```text
20260805_102127   기존 0회차 (4, 2, 12)  →  새 1회차 (4, 0, 0)
```

## 4. 검증

### 4.1 단위 테스트

**254 → 259건**, subtest 43건. 전부 통과.

- `RepairAbortTests` 3건 — 죽은 모델 호출에도 측정이 영수증에 남는지, 중단이
  영수증에 이름으로 남는지, 그 표식이 프로젝트 결함으로 세어지지 않는지
- 롤백 점수 2건 — 측정 공백이 두 번 세어지지 않는지, 실측된 역전 그대로
  고쳐진 쪽이 이기는지

### 4.2 실측

- §1의 라이브 2회 (영수증 `2026/08/05/20260805_102127_307_cf0597b...`)
- §2.1의 166건 스캔
- §3.2의 53건 재생

### 4.3 측정하지 않은 것

- **`repair_aborted` 경로는 라이브로 재현하지 않았다.** 2차 실행은 Ollama가 끊기지
  않아 그 경로를 타지 않았고, 단위 테스트로만 확인했다
- **바뀐 롤백 선택이 실제로 더 나은 결과를 내는지는 모른다.** 재생은 "무엇을
  고르는가"만 말하고, 고른 상태로 다음 사이클이 어떻게 됐을지는 말하지 않는다
- **코인 요청은 여전히 통과하지 못한다.** repair 3사이클이 전부
  `tool-call iteration limit reached`로 끝났고, 최종 `build_stage_success=False`,
  `component_missing:Player:Rigidbody`가 남았다. 이 요청 형태의 빌더 완결성은
  별개 문제다

열린 항목은 [STATUS.md](STATUS.md)에 있다(`AGENTS.md` §3.1).

  태그 하나로 12개가 blocked되고, 그것이 롤백 점수를 왜곡한 조건이었다
- **F** B0(v1.11.19의 라이브 확인), 완료된 측정의 유실
