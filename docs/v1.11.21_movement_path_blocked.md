# v1.11.21 — 막힌 방향을 배치 문제로 판정한다

`docs/STATUS.md` A1이다. v1.11.15가 실측하고 안내로 대응했다가 재발을 확인한 뒤
"하네스가 판정하게 한다"로 남겨 둔 항목이다.

---

## 1. 배경

시작 지점 옆에 플랫폼이 있으면 그 방향의 이동 거리가 짧아진다. 호스트는 그것을
`a_did_not_move_left`(또는 `d_did_not_move_right`)로 보고하고, 그 실패 코드의 수정
안내는 입력 코드를 가리킨다. **repair는 멀쩡한 스크립트를 고치러 가고, 코드를
고쳐서는 절대 통과할 수 없다.**

v1.11.15는 `fix_prompt`에 "한쪽이 현저히 짧으면 그 방향에 장애물이 있다"는 문장을
넣었지만 3차·5차에서 재발했고, 문서에 이렇게 적었다.

> 안내만으로는 재발한다. `movement_path_blocked` 같은 별도 코드로 갈라 repair가
> 입력 코드가 아니라 배치를 보게 해야 한다.

## 2. 판정 근거 — 기록된 119건의 분포

영수증에서 d와 a가 **동시에 측정된** 표본을 전부 뽑아 짧은 쪽/긴 쪽 비율을 봤다.

| 구간 | 비율 | 성격 |
|---|---|---|
| 정상 | **0.96 ~ 1.00** | 대다수 |
| — | 0.43 ~ 0.95 | **표본 없음** |
| 막힘 | **0.00 ~ 0.42** | 한쪽만 짧다 |

두 무리 사이가 비어 있어 임계값을 가정 없이 고를 수 있다. **0.5**는 그 빈 구간
한가운데다. 유일하게 애매한 표본 3.53/5.05(0.70)는 건드리지 않는다.

### 2.1 반드시 배제해야 하는 두 가지

- **양쪽 다 실패**하면 장애물이 아니라 입력 코드다. `0.0/0.0`과 `1.44/-1.46`이
  그 형태이고, 기존대로 `d_did_not_move_right` + `a_did_not_move_left`로 남아야
  한다. 그래서 **긴 쪽이 최소 거리를 넘겨 "이 방향은 된다"를 증명했을 때만** 성립한다
- **폭주 물리**는 비율이 낮게 나오지만 원인이 다르다. 실측 `D +2.5 / A −115.19`가
  비율 0.02인데 이것은 `a_moved_too_far`다. 긴 쪽이 상한 안에 있어야 한다

## 3. 변경 내용

`_blocked_movement_direction()`이 위 조건을 판정하고, 성립하면 개별 방향 실패 대신
`movement_path_blocked:<d|a>` 하나를 낸다. `bidirectional` 검사에 속하도록 매핑해
회귀 판정과 롤백 점수가 이것을 새 종류의 실패로 오해하지 않게 했다.

수정 안내는 코드를 만지지 말라고 명시한다.

> 왼쪽 이동은 정상인데 오른쪽만 짧게 끊겼다. 양쪽이 같은 코드를 쓰므로 **이것은
> 스크립트 결함이 아니라 배치 문제다 — 입력 코드를 고치지 마라.** 오른쪽에
> 플레이어와 같은 높이로 놓인 플랫폼·벽·중복 콜라이더를 찾아 치우거나 위로 올린다.
> (…) `unity_get_hierarchy`로 좌표를 확인한 뒤 `unity_modify_gameobject`로 옮긴다.
> 새 씬을 만들지 말고 스크립트도 다시 쓰지 마라.

## 4. 검증

### 4.1 기록된 119건 재생

| | 건수 |
|---|---:|
| 판정 유지 | **108** |
| 기존 실패를 배치 실패로 교체 | **7** |
| 조용히 통과하던 것을 새로 적발 | **4** |

**오탐 0.** 교체된 7건은 전부 한쪽이 5유닛 가까이 가고 반대쪽이 0~0.5에 그친 형태다.

```text
교체  20260723_125846  D 5.06  A  0.00   a_did_not_move_left  → movement_path_blocked:a
교체  20260723_125846  D 4.86  A  0.00   a_did_not_move_left  → movement_path_blocked:a
교체  20260723_125846  D 4.96  A  0.00   a_did_not_move_left  → movement_path_blocked:a
교체  20260723_130306  D 0.00  A −4.98   d_did_not_move_right → movement_path_blocked:d
교체  20260723_130306  D 4.89  A  0.00   a_did_not_move_left  → movement_path_blocked:a

신규  20260730_143859  D 2.06  A −4.95   (실패 없음)          → movement_path_blocked:d
신규  20260730_143859  D 2.06  A −5.05   (실패 없음)          → movement_path_blocked:d
```

### 4.2 판정이 뒤집히는 영수증은 하나다

새로 적발되는 4건 중 셋은 이미 다른 이유로 `failed`였다. **`20260730_113527`
하나만 `verified` → `failed`로 바뀐다.**

```text
20260730_113527  status=verified  검사 5/5  실패 0건
                 D +2.06 / A −5.05
```

오른쪽이 왼쪽의 41%밖에 못 갔는데 둘 다 최소 거리(2.0)를 넘겨 통과했다.
v1.11.15 §5가 기록한 그 배치 문제이고, 이 뒤집힘이 이 변경의 목적이다.

### 4.3 단위 테스트

**259 → 266건**, subtest 43 → 48건. 전부 통과.

- 오진 표본(0.47/−4.69)이 이제 배치를 지목하고 `d_did_not_move_right`는 나오지 않음
- 조용히 통과하던 표본(2.06/−5.05)이 실패로 잡힘
- **양쪽 실패(0.0/0.0, 1.44/−1.46)는 그대로 입력 결함**
- **폭주 물리(2.5/−115.19)는 `a_moved_too_far`로 유지**
- 정상 구간과 0.70 표본은 건드리지 않음
- 수정 안내가 "입력 코드를 고치지 마라"와 `unity_modify_gameobject`를 담음
- `bidirectional` 검사에 속함

### 4.4 측정하지 않은 것

**라이브 E2E를 돌리지 않았다.** 재생은 "무엇이 걸리는가"를 말하지만, repair가 이
안내를 받고 실제로 오브젝트를 옮겨 통과시키는지는 확인하지 않았다. 이 형태를 라이브로
재현하려면 시작 지점 옆에 벽이 있는 배치를 의도적으로 만들어야 한다.

임계값 0.5는 119건 분포의 빈 구간에서 골랐지만, **0.43~0.95 구간의 표본이 하나도
없다는 것은 그 구간이 안전하다는 뜻이 아니라 아직 관측되지 않았다는 뜻이다.**
그 구간의 실행이 나오면 다시 봐야 한다.
