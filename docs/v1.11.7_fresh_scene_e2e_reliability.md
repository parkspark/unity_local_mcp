# v1.11.7 — 엄격한 새 씬 전체 E2E 첫 통과 · 검증 배관 신뢰성 보강

작성일: 2026-07-29  
대상 버전: **v1.11.7**  
선행 문서: [인계 문서](HANDOFF_2026-07-29.md)

## 1. 배경

v1.11.4부터 `measured_checks`가 채워진 정당한 `verified` 영수증은 있었지만, 모두 이미
만들어진 산출물을 `--repair-existing`으로 고친 결과였다. 새 씬을 제작하는 전체 실행도
한 차례 통과했으나, 같은 씬 경로에 이전 실행 흔적이 있어 “진짜 빈 경로”의 증거로 쓰기
어려웠다.

이번 작업의 합격 기준은 다음과 같이 엄격하게 잡았다.

1. 실행 직전에 대상 `.unity`와 `.unity.meta`가 모두 없어야 한다.
2. `--repair-existing` 없이 표준 CLI를 실행한다.
3. Unity 제작과 도구 호출은 로컬 모델 `qwen3-coder:30b`가 수행한다.
4. 호스트 검증 영수증이 `status=verified`, 요청 검사 전부 측정,
   `skipped_checks=[]`를 기록해야 한다.

최종 대상은 실행 전에 존재하지 않았던
`Assets/Scenes/PlatformerMovementJumpV1117Strict2.unity`다.

```bash
uv run python main.py --project "C:\Users\park\My project (55)" \
  --prompt-file prompts/platformer_movement_jump_fresh_scene.txt
```

## 2. 변경 내용

### 2.1 repair와 rollback 판정

- `_repair_score()`가 실제 결함보다 측정 범위를 먼저 비교한다. 검사를 하나도 못 한
  차단 상태를, 검사를 실행해 결함을 발견한 상태보다 좋다고 보지 않는다.
- 같은 검사 안에서 실패 형태가 바뀌는 것은 새 회귀로 취급하지 않는다.
- rollback 직후에는 asset refresh가 가능하도록 도구 모드를 복원한다.
- 복원된 씬 파일을 다시 열어, 폐기한 repair의 컴포넌트가 메모리 씬에 남는 혼합 상태를
  재검증하지 않게 했다.

### 2.2 Play Mode 도메인 리로드 대응

Unity는 Play 요청을 받은 뒤 도메인 리로드 동안 `isPlaying=false`를 수 초간 돌려줄 수
있다. 고정 0.7초 대기 대신 0.5초 간격으로 최대 10초 동안 활성 상태를 확인한다.
검증 계약도 Play가 한 번 실제 활성화된 뒤에만 `false` 전환을 예기치 않은 종료로 센다.

리로드 후 새 에디터 도메인에서 브리지 리스너가 다시 열리지 않는 문제도 확인했다.
형제 저장소 `unity_mcp/UnityBridge/UnityMcpBridge.cs`와 테스트 Unity 프로젝트에
Entered Play/Edit Mode 재시작 및 지연 재바인딩 초기화를 적용했다. 실제 Unity에서
약 4.3초 리로드 뒤 `[McpBridge] Listening`과 TCP 8722 LISTENING을 확인했다.

### 2.3 컴파일 오류의 내구성

도메인 리로드가 브리지의 메모리 콘솔 버퍼를 비우면, 컴파일 실패 때문에 Play Mode에
진입하지 못했는데도 `unity_read_console`이 오류 0건을 반환했다. `mcp_client.py`가
프로젝트 `Logs/Editor.log`의 최신 Tundra 빌드 결과만 읽어, 최신 빌드가 실패한 경우의
C# 오류를 콘솔 결과에 보충한다. 이후 성공 빌드가 있으면 과거 오류를 되살리지 않는다.

현재 컴파일 오류가 정확히 지목한 `Assets/Scripts/*.cs`는 충돌 스크립트 정리에 한해
삭제할 수 있게 했다. 임의의 기존 스크립트 삭제는 계속 차단하며, 관련 없는 콘솔 문장은
권한을 만들지 않는다.

### 2.4 작업 범위와 입력 지침

- 사용자가 레벨·스테이지·LevelLoader·레벨 JSON·데이터 주도 워크플로를 요청하지 않으면
  레벨 로더 도구를 차단한다.
- 간단한 키보드 게임은 `Keyboard.current`를 직접 사용하고 불필요한 `PlayerInput`,
  InputAction/생성 controls/handler를 만들지 않도록 시스템 및 repair 지침을 강화했다.
- 짧은 점프 tap은 `Update`에서 latch하고 `FixedUpdate`에서 소비하도록 안내한다.

### 2.5 일시적 모델 오류 재시도

도구 호출을 반환하기 전 발생한 Ollama EOF·연결 오류·408·429·일시적 5xx는 부작용이
없으므로 기본 1회 재시도한다. 비재시도 오류는 즉시 전달한다. 횟수는
`UNITY_AGENT_MODEL_RETRIES`로 조정한다.

### 3.2 엄격한 새 씬 로컬 모델 E2E

최종 실행 로그:

| `skipped_checks` | `[]` | **`[]`** |
| 최종 실패 | 이동·점프·rollback | **없음** |
| 경과 시간 | 163.156초 | **179.110초** |

최종 영수증:

```text
status           = verified
build_stage_success = false
requested_checks = [gameplay, movement, bidirectional, jump, components:Player]
measured_checks  = [gameplay, movement, bidirectional, jump, components:Player]
skipped_checks   = []
failures         = []
```

첫 검증은 저장되지 않은 씬 때문에 동작 검사가 차단됐다. 첫 repair 뒤 A/D 이동은
각각 약 4.95유닛으로 측정됐지만 점프가 실패했고, 두 번째 repair가 점프 입력 latch와
ground check를 고쳐 상승과 착지까지 통과했다. 전체 과정은 하나의 표준 CLI 실행 안에서
로컬 모델이 수행했으며, Codex가 Unity 제작 도구를 대신 호출하지 않았다.

`build_stage_success=false`는 남아 있다. 이는 전체 파이프라인 실패가 아니라 빌더의 첫
산출물이 자체 완료 조건을 만족하지 못해 같은 실행의 repair가 완성했다는 뜻이다.

## 5. 남은 과제

1. **빌더 자체 완결성**: `build_stage_success=true`인 새 씬 E2E를 확보한다. 특히 빌더가
   첫 검증 전 씬을 저장하고, 간단한 키보드 요청에서 불필요한 PlayerInput 경로를 만들지
   않도록 해야 한다.
2. **repair 반복 효율**: 이번 실행도 두 repair 사이클이 필요했다. 반복 탐색과 무효 도구
   호출을 줄여 모델 호출 예산을 낮춘다.
3. **브리지 회귀 테스트**: 실제 Unity에서 리스너 재시작은 확인했지만, C# 에디터 도메인
   리로드 자체를 자동화한 테스트는 아직 없다.
4. **퇴화 요청과 외부 경계**: 문맥 의존 짧은 요청, MCP stdio·포트 호핑·창 포커스·모달
   자동화의 테스트 공백은 남아 있다.
