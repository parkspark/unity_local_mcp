# v1.11.14 — 부분 집합을 전체로 판정하는 것을 보이게 하기 · 사용자 문장이 드러낸 추출 공백

작성일: 2026-07-30
대상 버전: **v1.11.14**
선행 문서: [개선 보고서 2026-07-30](improvement_report_2026-07-30.md) · [v1.11.13](v1.11.13_empty_spec_and_project_guard.md)

## 1. 배경

개선 보고서가 P0로 지목한 것은 이것이었다.

> `measured_checks`가 비어 있지 않으므로 v1.11.13의 `verification_spec_empty` 가드에
> 걸리지 않는다. 이동만 측정하고 `verified`가 나가는데, 사용자가 요청한 핵심
> 기능(점수·소멸·클리어)은 한 번도 확인되지 않는다.

v1.11.2가 잡은 것이 "빈 집합을 성공으로 판정"이라면 이것은 **"부분 집합을 전체로
판정"**이다. 이번 사이클은 P0와, 보고서가 P2-1로 둔 **빌더 예산 분류 로깅**을 함께
넣었다. 둘 다 판정 로직을 바꾸지 않는 **기록 단계**다.

## 2. 변경 A — `unmapped_requirements`

### 2.1 하는 일

요청을 문장 → 절로 쪼개고, 조건·결과 표현(`~에 닿으면`, `획득`, `점수`, `체력`,
`사라지`, `클리어`, `스폰`, `격자`, `순찰`, `on collision` …)을 담은 절 중에서 **지금
검사 어휘가 한 마디도 하지 못하는 것**을 골라 영수증과 화면에 남긴다.

`verified` 판정은 **바꾸지 않는다.** 게이트로 만들지 않은 이유는 v1.11.10이 게이트
오탐으로 예산 8회를 태운 전례 때문이다. 먼저 실제 프롬프트에서 오탐률을 보고, 막을지는
그 데이터로 정한다.

### 2.2 설계에서 두 번 고친 것

첫 구현은 감지 5건 중 **3건을 놓치고 오탐 2건**을 냈다. 원인 두 가지를 실측으로 잡았다.

1. **문장 분리가 경로에서 깨졌다.** `Assets/Scenes/A.unity`의 마침표가 문장 끝으로
   잡혀 절이 `unity 경로에 새 빈 씬을…`로 시작했다. 마침표는 **뒤에 공백이나 끝이 올
   때만** 문장 경계로 본다.
2. **절 단위 판정이 너무 컸다.** `Player가 A/D로 이동하고 코인에 닿으면 점수가 1
   올라가게`는 한 문장 안에 측정되는 절반과 측정되지 않는 절반이 같이 있다. 문장에
   `이동`이 있다는 이유로 통째로 건너뛰면 **탐지하려는 바로 그 실패를 재현**한다.
   `하고`/`해서`/`그리고`/쉼표로 한 번 더 쪼갠 뒤 판정한다.

씬 이름도 오염원이었다. `GridProceduralRepro1.unity`의 `Grid`가 마커에 걸려 씬을
만들기만 하는 문장이 요구사항으로 잡혔다. `Assets/...` 토큰은 먼저 제거한다.

### 2.3 감지 품질 (실측)

| 대상 | 결과 |
|---|---|
| 저장소의 실제 프롬프트 32개 | **오탐 0** — 격자 프롬프트 2개만 감지(정탐, 실제로 미지원 형태) |
| 덮이지 않는 요청 5종 | **5/5 감지** |

```text

적 순찰    checks=0  → "... 적이 좌우로 자동 순찰하게 구현해줘"
```

  · Player가 코인에 닿으면 점수가 1 올라가게 해줘

## 3. 변경 B — 빌더 예산 분류 로깅 (P2-1)

### 3.1 배경

`builder_stage_evaluated` 기록 38건 중 **37건이 `model_loop_completed=false`**이고,
빌더 단계 어시스턴트 턴이 측정한 실행 전부에서 정확히 31(`MAX_ITERS=30`)이었다.
예산이 매번 소진된다.

손으로 센 표본 하나(BoostDashRepro2)에서 빌더 32회 중 16회가 자기 입력 테스트였고,
호스트가 직후에 독립적으로 다시 쟀다. 다만 **표본 하나로 예산을 깎는 것은 이 저장소가
반복해서 손해 본 방식**이라(v1.11.9의 예산 오진), 먼저 로그에 남기게 했다.

### 3.2 하는 일

빌더 단계의 모든 도구 호출을 `build`(상태를 바꿈) / `self_check`(읽기·재생·입력) /
`rejected`(정책 차단) / `other`로 세어 `builder_stage_evaluated`에 함께 기록한다.

### 3.3 첫 데이터가 가설을 반박했다

| 실행 | build | self_check | rejected | 자가 검증 비중 |
|---|---:|---:|---:|---:|
| CoinScoreRepro1 | 28 | 1 | 1 | **3%** |
| Jump13 | 7 | 20 | 1 | **69%** |

**요청에 따라 정반대다.** 코인/점수 실행은 예산 전부를 제작에 썼고, 점프 실행은 2/3을
자기 검증에 썼다. "빌더가 예산의 절반을 중복 자가 검증에 쓴다"는 표현은 점프 형태에는
맞고 일반적으로는 틀리다.

**따라서 이번 사이클에서 예산을 손대지 않았다.** 무엇을 줄일지는 형태별 분포가 더
쌓인 뒤에 정한다. 지금 일괄로 자가 검증을 막았다면 코인 실행에는 아무 효과가 없고
점프 형태의 빌더 완결성만 위태로워졌을 것이다.

## 4. 사용자가 준 실제 문장이 드러낸 것

§2가 만든 탐지기의 오탐률을 보려면 이 저장소가 쓴 프롬프트가 아니라 **사용자가 실제로
입력하는 문장**이 필요하다. 사용자가 하나를 줬다.

```text
3층짜리 플랫폼을 만들어. ad키로 좌우로 움직이고, space가 점프, 좌쉬프트키를 누르면
순간적으로 방향키 방향으로 가속하게해. 카메라를 추가해서 플레이어를 추적하게해.
```

정적 추출 결과는 이랬다.

```text
requested_checks : ['gameplay', 'movement', 'jump', 'components:Player']
이동키           : rightArrow / leftArrow      ← 요청은 ad키
boost            : False                      ← 요청에 있음
camera_follow    : False                      ← 요청에 있음
bidirectional    : False                      ← 요청은 "좌우"
```

**요청한 네 기능 중 점프 하나만 제대로 잡혔고, 이동은 틀린 키로 측정하려 했다.**
A/D로 올바르게 구현한 게임을 하네스가 떨어뜨리는 상태다 — v1.11.4가 고친 것과 같은
계열의 결함이 네 군데서 동시에 나왔다.

| 공백 | 원인 | 수정 |
|---|---|---|
| 이동키가 방향키로 | `_AD_SCHEME`이 구분자 있는 `a/d`만 인식. `ad키`에는 구분자가 없어 실패하고, "방향키 방향으로 가속"의 `방향키`가 대신 잡혔다 | `ad키`·`AD 키`·`a와 d` 표기 추가 |
| 양방향 검사 누락 | `\ba\b`와 `\bd\b`를 각각 찾는데 `ad키`에는 둘 다 없다 | A/D 스킴 일치 또는 `좌우`/`양쪽`/`양방향`으로 판정 |
| 부스트 미감지 | 문맥어가 라틴 `shift`뿐 | `쉬프트`·`시프트` 추가 |
| 카메라 추종 미감지 | 추종 어휘에 `추적`이 없음 | `추적`·`쫓`·`track` 추가 |

수정 후:

```text
requested_checks : ['gameplay', 'movement', 'bidirectional', 'jump',
                    'camera_follow', 'boost', 'components:Main Camera', 'components:Player']
이동키           : d / a
unmapped         : ['3층짜리 플랫폼을 만들어']
```

검사가 4개에서 8개로 늘었고, **어휘에 없는 것 하나(층수)만 미매핑으로 남았다.**
§2의 탐지기가 의도대로 동작한 첫 외부 문장이다. 저장소 프롬프트 32개에 대한 회귀는
없었다(키 스킴 이상 0건).

### 4.1 라이브 실행이 다시 두 가지를 드러냈다

같은 요청을 새 씬 경로로 세 번 돌렸다.

| | 1차 | 2차 | **3차** |
|---|---|---|---|
| `status` | failed | failed | **verified** |
| 측정된 검사 | 8/8 | 8/8 | **8/8** |
| 부스트 비율 | **1.04** (하한 1.4) | 2.10 | **2.03** |
| 점프 상승 | +1.00 | **0.00** | **+1.96 · 착지 true** |
| 사이클 | 3 | 4 | **2** |

**1차 — 부스트 실패에 수정 안내가 아예 없었다.** 모델은 대시를
`AddForce(..., ForceMode.Impulse)`로 줬는데, 같은 FixedUpdate가
`rb.linearVelocity = new Vector3(axis * moveSpeed, ...)`로 수평 속도를 통째로 대입해
그 impulse를 즉시 지웠다. 측정 비율 1.04. `fix_prompt`에는 `boost_distance_too_short`
항목이 없어 repair 2회가 원인을 못 짚었다. 이 상호작용을 그대로 설명하고, 대시를 속도
대입 자체에 반영하는 형태와 **호스트가 어떻게 측정하는지**(이동키+leftShift 0.5초,
같은 시간 일반 이동과의 비율)를 함께 주도록 추가했다. 2차·3차 모두 **첫 repair에서
해결**됐다.

**2차 — 점프 실패가 코드가 아니라 배치였다.** 상승량이 정확히 `0.00`이었고 스크립트의
rising edge 래치·접지 판정은 정상이었다. 씬을 보면 원인이 나온다.

```text
Floor1  y=0, scale.y=1  → 윗면 0.5
Floor2  y=3, scale.y=1  → 아랫면 2.5
Player  y=1             → 캡슐 상단 ≈ 2.5
```

**세 층을 같은 X 위에 쌓아 Player 머리 바로 위가 다음 층 바닥이었다.** 물리적으로 뛸
수 없는 배치이고, 코드만 고치라는 안내로는 repair가 이 원인에 닿을 수 없다. 이미
`a_did_not_move_left`에 "시작 평지를 확보하라"는 배치 안내가 있던 것과 같은 계열이라,
`player_did_not_jump`에도 배치를 의심하라는 항목을 넣었다 — 상승량이 정확히 0이면
천장을 먼저 보고, 층은 수직으로만 쌓지 말고 X 방향으로 어긋나게 배치하라는 것이다.
3차는 점프 `+1.96`, 착지 true로 통과했다.

### 4.2 두 번째 사용자 문장 — 어휘가 두 모듈에서 갈라져 있었다

```text
새씬을 열어서, 2.5D 플랫포머 게임을 만들어줘. ad로 좌우로 움직이고, space로 점프를 해.
쉬프트를 누르면 이동중인방향으로 빠르게 일정거리를 x축 직선이동을 함.
카메라가 있어서 2.5D 뷰를 보여주며 플레이어를 추적함.
```

§4의 수정을 하고도 네 군데가 또 어긋났다. 이번 원인은 어휘 자체가 아니라 **같은 뜻의
어휘를 두 모듈이 따로 들고 있던 것**이다.

| 공백 | 결과 |
|---|---|
| `ad로` — §4에서 `ad키`만 추가했다 | 이동키가 다시 방향키로, `movement_keys_explicit=False` |
| `task_contract._direct_keyboard_keys`가 자기 정규식을 따로 가짐 | 게이트가 `spaceKey`만 강제 — A/D를 읽지 않는 스크립트가 통과 |
| `fresh_scene_requested`에 `새씬`(붙여쓰기) 없음 | 새 씬 정책(미정의 태그·기존 스크립트 재사용 차단)이 통째로 꺼짐 |
| `camera_requested`가 `추적`을 모름 | v1.11.12의 빈 템플릿 차단이 꺼짐 |

그리고 `` 경계에서 세 번째 결함이 나왔다. **한글은 단어 문자라서 `D로`의 `d`와 `로`
사이에 경계가 없다.** `d`는 `A, D로 이동`을 통째로 놓친다 — `_has_word`가 문서에
적어둔 바로 그 이유인데 `_AD_SCHEME`은 ``를 쓰고 있었다. 라틴 문자에 대해서만 경계를
정의하도록 고쳤다.

구조적 원인이 두 번 같은 결함을 냈으므로 **요청 문구 어휘의 단일 출처를 정했다.**
`verification.py`가 `AD_SCHEME` · `CAMERA_WORDS` · `CAMERA_FOLLOW_WORDS` ·
`FRESH_SCENE_PHRASES` · `has_word`를 공개하고 `task_contract`가 그것을 쓴다. 갈라지면
바로 실패하도록, 여섯 가지 표기에 대해 **게이트가 강제하는 키 ⊇ 호스트가 측정하는 키**를
확인하는 테스트를 넣었다.

수정 후 검사 9개(`gameplay, movement, bidirectional, jump, camera_follow, boost,
screenshot, components:Main Camera, components:Player`), 이동키 `d/a`, 게이트 강제키
`aKey·dKey·spaceKey`, 새 씬·카메라 정책 모두 켜짐, 미매핑 0건.

라이브(`20260730_141150_542_e8f7152452.json`)는 **verified · 9개 전부 실측 · repair 1회**.
첫 검증이 아무것도 측정하지 않고 실패했는데, 로그를 보면 빌더 산출물에서 **플레이어가
바닥 없이 낙하하고 있었다**(y 1.0 → −27.96). 호스트가 불안정한 상태를 측정하는 대신
거부한 것이라 설계대로 동작했다.

### 4.3 되돌린 것 — 근거가 틀렸던 카메라 상한

이 실행의 `camera_follow_delta`가 `16.08`인데 플레이어 이동은 `5.06`이라, 카메라가
3배로 달아나는데도 통과한다고 보고 상한을 넣었다. **오독이었다.** `camera_follow_delta`는
검증 세션 전체(d·a·부스트·점프)의 누적 이동이고, 판정이 실제로 쓰는 값은 라벨별
측정값이다. 오늘 기록된 카메라 측정 20건을 재생해 보니 최종 측정에서 카메라 이동이
플레이어 이동과 **전부 0.04 이내로 일치**했다.

`camera_follow`에 상한이 없는 것은 사실이지만(이동은 v1.11.4, 점프는 v1.11.9에서 받았다)
**달아나는 카메라의 실측 사례는 없다.** 사례 없이 검사를 늘리는 것은 v1.11.7의
`.bounds`가 v1.11.10에서 되돌려진 방식이므로 추가한 상한을 제거하고, 관측될 때 넣도록
주석으로 남겼다.

### 4.4 남은 것

세 실행 모두 `build_stage_success=false`다. 기능 네 개가 얽힌 이 요청은 빌더가 아직
한 번도 혼자 끝내지 못했다. 점프·카메라 단일 형태에서 얻은 완결성이 복합 요청으로는
일반화되지 않는다는 뜻이고, 이것이 다음 사이클의 재료다.

## 7. 남은 과제

1. **`camera_follow`의 상한** — 하한만 있다(§4.3). 달아나는 카메라의 실측 사례가
   나오면 그때 넣는다.
2. **오탐률 표본을 더 넓힌다.** 저장소 프롬프트 32개 + 사용자 문장 1개에서 오탐 0이다.
   외부 문장은 아직 하나뿐이고, 그 하나가 추출 공백 넷을 드러냈다(§4). 막는 쪽으로
   갈지는 표본이 더 쌓인 뒤 정하고, 갈 때는 `verification_spec_empty`처럼 실패로 처리한다.
3. **복합 요청의 빌더 완결성.** 기능 넷이 얽힌 사용자 요청은 세 번 모두
   `build_stage_success=false`였다. 단일 형태에서 얻은 완결성이 일반화되지 않는다.
4. **상태 변화 검사군**(개선 보고서 P1) — 오브젝트 개수 / 소멸 / 컴포넌트 필드 값 변화.
   §2가 만들어내는 미매핑 절 목록이 어떤 검사부터 필요한지 알려주는 입력이다.
   격자 형태도 여기서 함께 풀린다.
5. 빌더 예산 — 형태별 `builder_calls` 분포가 더 쌓인 뒤에 결정한다(§3.3).
6. 브리지 도메인 리로드·held-key 재큐잉의 Unity 통합 회귀 테스트.
