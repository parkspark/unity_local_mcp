# v1.11.16 — 만들어졌는지 보지 않고 통과하던 두 자리

`scene_objects`와 `player_visible`을 추가했다. 둘 다 관측된 영수증 한 건씩을 근거로
하고, 기록된 계층 판독 73세션을 재생해 오탐 0건을 확인한 뒤 넣었다.

---

## 1. 배경

### 1.1 결함 A — 생성 요청이 검사 0개로 통과했다

`logs/receipts/2026/08/01/20260801_202621_246_08b6891343.json`:

```text
request          : 댕댕이 모양의 모델링 생성해줘
status           : verified
elapsed_seconds  : 22.359
requested_checks : []
measured_checks  : []
failures         : []
```

**22초, 검사 0개, `verified`.** 호스트가 실제로 본 것은 두 가지뿐이다 — 컴파일 오류
0건, 활성 씬이 저장됨. 개가 만들어졌는지는 아무도 보지 않았다.

이 저장소는 v1.11.2부터 "측정하지 않은 것을 성공으로 판정"과 싸워 왔고, 가드가 이미
두 개 있다(`verification.py`의 `verification_spec_empty`).

| 가드 | 발동 조건 | 이 요청 |
|---|---|---|
| v1.11.2 계열 | 런타임 어휘가 있는데 behaviour 검사가 없음 | `behaviour_requested=False` → 비껴감 |
| v1.11.14 계열 | 생성 + **검증 요구**인데 검사가 없음 | `verification_requested=False` → 비껴감 |

"생성해줘"는 검증을 명시하지 않았고 런타임 동작을 말하지도 않았다. **두 가드 사이의
구멍**으로 나간 것이지, 가드가 잘못 판단한 것이 아니다.

`docs/improvement_report_2026-07-30.md` §2가 "검사 어휘 전체가 플레이어가 어떻게
움직이는가 한 축"이라고 적은 그 바깥이며, §3 P0("부분 커버리지의 조용한 통과")과 같은
계열이다. P0은 라이브 관측 표본을 기다리고 있었는데, 이 영수증이 그 표본이다 —
부분이 아니라 **전무**라는 점만 다르다.

### 1.2 결함 B — 렌더러 없는 Player가 검사 13개를 전부 통과했다

`logs/receipts/2026/07/31/20260731_033338_195_471258ba7b.json`:

```text
status          : verified      elapsed_seconds : 286.672
measured_checks : 13개 전부     skipped_checks  : []
failures        : []            unmapped_requirements : []
```

그런데 Game View에 플레이어가 없었다. 같은 실행의 계층 판독
(`logs/mcp/2026/07/31/20260731_032824_506_*.jsonl`)에 원인이 그대로 있다.

```text
Player  components = [Transform, Rigidbody, BoxCollider, PlayerController]
```

**MeshFilter도 MeshRenderer도 없는 빈 GameObject다.** 물리는 완벽히 동작했으므로
이동·점프·부스트·카메라 추종이 전부 실측 통과했고, 화면에 그릴 것만 없었다.

`verification.py`의 `components["Player"]`는 `["Rigidbody", "Collider"]`만 요구한다.
**렌더러를 보는 검사는 어디에도 없었다.** `docs/demo_prompt_soloai_2026.md` §3.5가
"아직 열려 있다"고 적어 둔 항목이다.

## 2. 변경 내용

### 2.1 `scene_objects` — 씬에 무엇이 생겼는가

씬에 실체가 남아야 하는 생성 요청에 붙는다. 조건은 **생성 동사 + 씬에 존재해야 하는
대상**이다(`_CREATE_WORDS` × `_SCENE_OBJECT_WORDS`, 또는 게임·레벨·behaviour 요청).

검증 단계가 Edit Mode에서 `unity_get_hierarchy`를 한 번 읽고, 활성 씬의 루트
오브젝트에서 새 씬이 기본으로 갖는 것(`Main Camera`, `Directional Light`,
`Global Volume`)을 뺀 나머지를 센다.

| 결과 | 실패 코드 |
|---|---|
| 계층을 읽지 못함 | `scene_contents_not_observed` |
| 기본 오브젝트뿐 | `scene_has_no_created_objects` |

영수증 증거에 `scene_objects`로 **이름 목록이 그대로 남는다.** 8/1 요청을 그
실행이 실제로 기록한 계층 페이로드로 재생하면 이렇게 나온다.

```text
requested_checks : ['scene_objects']
scene_objects    : ['DogBody', 'DogHead', 'DogEarLeft', 'DogEarRight',
                    'DogTail', 'DogEyeLeft', 'DogEyeRight', 'DogNose']
```

같은 요청이 이제 22초에 0개가 아니라 **측정 1개**로 끝난다. 그 실행은 실제로 개를
만들었으므로 판정은 여전히 통과이고, 달라진 것은 통과에 근거가 생겼다는 점이다.

### 2.2 기존 거절을 약화시키지 않는다

`scene_objects`는 v1.11.14가 세운 거절을 **혼자 취소하지 못한다.**

"10x20 격자 보드를 Awake에서 코드로 생성 ... 실제로 생성되는지 검증까지 끝내줘"는
새 씬을 만들라고 하므로 `scene_objects`가 붙는다. 그런데 격자는 런타임에 생성되고,
Edit Mode 계층에는 그것을 만드는 MonoBehaviour 호스트 오브젝트 하나만 보인다.
그 오브젝트의 존재를 "보드가 만들어졌다"의 증거로 인정하면 **이 가드가 막으려던
바로 그 영수증이 다시 나온다.**

그래서 명시적 검증 요구에 대한 empty-spec 판정은 `scene_objects`를 제외한 검사
집합으로 한다. 부작용으로 "큐브 만들고 실제로 생성됐는지 확인해줘" 같은 요청은
계속 거절되는데, 이는 v1.11.15까지의 동작과 같으므로 회귀가 아니다.

### 2.3 `player_visible` — Player가 화면에 그려지는가

`required_components`에 `Player`가 들어가는 요청(이동 또는 점프)에 자동으로 붙는다.
같은 계층 판독을 재사용하므로 추가 호출이 없다.

**자기 자신 또는 자식 어디에든** 이름이 `Renderer`로 끝나는 컴포넌트가 있으면 통과한다.
몸통과 머리로 나뉜 Player도 화면에는 보이므로, 자기 자신만 보면 그 구조가 오탐이 된다.

| 결과 | 실패 코드 |
|---|---|
| Player를 계층에서도 컴포넌트 조회에서도 못 봄 | `player_visibility_not_measured` |
| Player는 있는데 서브트리에 렌더러가 없음 | `player_has_no_renderer` |

이 실패는 다른 단계를 **차단하지 않는다.** 물리는 멀쩡하므로 이동·점프 측정은
그대로 돌아가고, 렌더링 결함 하나만 보고된다. `required_components`에 넣었다면
정적 게이트가 모든 단계를 blocked로 만들어 영수증이 원인을 잃었을 것이다.

수정 안내는 물리가 아니라 메시를 짚는다 — 프리미티브로 다시 만들면 MeshFilter와
MeshRenderer가 함께 붙는다는 것, 빈 GameObject에 Collider만 붙이지 말라는 것.
`agent.py` 빌더 프롬프트에도 같은 규칙을 넣어 repair 이전에 예방되도록 했다.

### 2.4 두 검사 모두 정적이다

`behaviour_checks()`의 정적 집합에 넣었다. Edit Mode 계층 조회로 끝나는 검사가
Play Mode 증명으로 계산되면 v1.11.2 가드의 뜻이 무너진다.

## 3. 검증

### 3.1 기록된 계층 판독 재생 — 오탐 측정

`logs/mcp/` 전체에서 계층 페이로드 **211건**을 뽑고, 세션마다 마지막 판독(빌드가 끝난
시점에 가장 가까운 상태) **73건**에 새 판정을 그대로 걸었다.

| | 건수 |
|---|---:|

**220 → 235건, subtest 40 → 43건.** 전부 통과.

### 3.4 라이브로 확인하지 않은 것

**실패 경로는 라이브로 재현하지 않았다.** `scene_has_no_created_objects`와
`player_has_no_renderer`가 실제 실행에서 발동해 repair로 이어지는 과정은 기록된
계층 재생(§3.1)과 단위 테스트(§3.2)로만 확인했다. 결함을 주입해 돌려 보는 것이
남아 있다.

## 4. 남은 과제

1. **실패 경로의 라이브 확인.** 통과 경로는 §3.3에서 2/2로 측정했지만, 렌더러를
   떼거나 빈 씬을 만들어 두 실패 코드가 실제로 발동하고 repair가 그 안내를 따라
   고치는지는 아직 보지 않았다(§3.4).
2. **`scene_objects`는 개수도 구조도 세지 않는다.** 오브젝트가 하나라도 있으면
   통과하므로 `docs/HANDOFF_2026-07-29.md` §3의 "스테이지가 절반만 생성돼도
   `verified`"는 그대로 열려 있다. 무엇을 세야 하는지는 아직 데이터가 없다.
3. **런타임 생성물은 여전히 측정 불가.** Awake/Start에서 만들어지는 격자·보드는
   Edit Mode 계층에 없다. 지금은 정직하게 거절하는 것으로 끝난다.
4. **생성 동사가 없는 수정 요청**은 아직 검사 0개로 통과할 수 있다. 관측된 표본이
   없어 가드를 넓히지 않았다 — 넓히면 정상적인 편집 요청까지 막는 v1.11.2의
   반대 오류가 된다.
5. v1.11.15 §7의 항목은 그대로 남았다 — `movement_path_blocked`(막힌 배치를 코드
   결함으로 오진, 표본 2건), `camera_is_player_viewpoint`의 라이브 확인, P1 상태 변화
   검사군, 브리지 도메인 리로드·held-key 재큐잉의 Unity 통합 회귀 테스트.
